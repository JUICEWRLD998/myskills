**Scope:** lending markets, collateralised debt, leveraged positions, auction/refinance/liquidation engines. Ordered by expected yield (fund loss first, then protocol-insolvency, then griefing/DoS). Derived from `LIQUIDATION-ISSUES/`, `Lending/`, and the lending material in `BEEDLE/`.

- **Dust / liquidation-incentive death-spiral (no minimum position size)** — Trigger: a borrow/mint path with a minimum *collateral* check but no minimum *borrow* amount, and a liquidation bonus that is a fixed percentage rather than scaled to size — look for `minLoanSize`-style checks present on one of the borrow/withdraw/mint paths and absent on the others. · Test: do the money arithmetic at the protocol's own floor before reading any logic. For a position at the cheapest size it permits (e.g. $6 collateral against $4 debt, 10% bonus, ~$2 gas) compute `liquidatorProfit = (seizedCollateralValue × bonusPct) − protocolFee − gasCost` and confirm it is negative; then prove no floor prevents creating that position, and that the liquidation function itself has no minimum-seizure or gas-aware threshold. · Impact: every unit of debt below the break-even size is economically uncollectible — a rational liquidator's expected profit is negative, so the position is never cleared. Each one is a permanent unit of bad debt that is socialised to lenders, and because the position is cheap to create and requires no capital beyond the dust collateral, an attacker can mint uncollectible bad debt at scale for the price of gas. The protocol's entire safety mechanism is inoperative across the whole sub-break-even band of its position size distribution. · FP guard: safe where a protocol-owned or subsidised liquidator exists, where the bonus scales with position size, where a minimum *borrow* size (not just a minimum deposit) is enforced on every mutating path, or where sub-floor positions are auto-written-off or auto-closed — and verify the liquidation function is actually permissionless before claiming the bug, since a keeper-only liquidation path makes the profit calculus irrelevant.
- **Attacker-supplied collateral token in the liquidation entrypoint** — Trigger: the liquidation signature takes the collateral asset as a parameter (`liquidate(IERC20 collateralToken, address position)`) and derives price and balance from it instead of from stored position state. · Test: call the liquidation path with a *different* registered token, an unregistered token, and `address(0)`, and check whether the computed collateral ratio changes while position state is untouched. · Impact: full seizure of a solvent borrower's collateral — the attacker repays a real debt at 0-token "collateral value" and takes the position; direct, unbounded, per-position theft. · FP guard: safe when the asset is derived from the position record and the input is only used as an assertion (`require(asset == pos.collateralToken)`); also check the token was allowlisted at position open, not just at liquidation.
- **Valuation source mutable after origination** — Trigger: a post-origination update function (`updateLoanParams`, `setOracle`, `setPriceFeed`, `updateCollateralConfig`) whose "no worse for the borrower" guard enumerates duration/valuation/interest/LTV but omits the oracle address or price-feed id. · Test: read the guard's require list and diff it against every field of the params struct; then check whether the oracle field is reachable in the same struct. · Impact: lender (or any authorised updater) points the position at an under-reporting oracle, the position becomes "underwater" on demand, and collateral worth multiples of the loan is seized. · FP guard: safe if the oracle is immutable, timelocked behind a delay longer than the loan term, or the same oracle is snapshotted into the position at origination.
- **Liquidator's collateral share measured against one debt tranche** — Trigger: `liqSize = pos.collateralSize * share / oldShare` where `oldShare = pos.debtShareOf[debtToken]` — a per-asset share — while collateral is shared across all of the borrower's debt. · Test: build a position with two debt assets (large + small) and liquidate only the small one; check whether the seized collateral is proportional to the amount repaid or to the repaid tranche's share. · Impact: repay the smallest debt tranche and receive the entire collateral; the remaining debt becomes unbacked bad debt. · FP guard: safe if the divisor is total position debt (`getDebtValue(positionId)`) or if collateral is segregated per debt asset.
- **Committed collateral overwritten to zero after offer validation** — Trigger: `commitCollateral(loanId, token, amount)` sets `collateralInfo[token] = amount` unconditionally and ignores the `false` returned by `EnumerableSet.add()` when the token is already present. · Test: commit non-zero collateral, let the offer be validated/accepted, then re-call the same function with `amount = 0` (or a second token address) and confirm the recorded collateral is now zero while the loan is live. · Impact: lender funds a loan that has no collateral to seize; 100% loss of the principal on default. · FP guard: safe if the function reverts on an existing token, requires `amount > 0`, or is restricted to the pre-acceptance state.
- **State deleted then read in the same function** — Trigger: `if (repaid == loan.amount) delete loans[loanID];` followed later in the same body by a use of `loan.lender` / `loan.owner` (a storage pointer, so it now reads zero). · Test: grep every function for `delete <mapping>[key]` and list every later read of a member of that struct in the same function. · Impact: the payout goes to `address(0)`; tokens that don't revert on a zero-recipient transfer silently burn the principal — total, permanent loss to the counterparty. · FP guard: safe if the delete is on a `memory` copy, is the last statement, or is followed by an immediate `return`.
- **Mapping default accepted as valid, paired with an unchecked counter** — Trigger: `Credit memory c = credits[id];` with no existence sentinel, then a guard like `if (c.principal > 0) revert` that a zero-struct passes, then `unchecked { --count; }`. · Test: call the state-changing function with an id that was never created, repeatedly, and watch the counter; when it reaches zero check whether a facility-wide status flips to `REPAID`. · Impact: the facility is reported repaid with nothing repaid; the borrower walks away from the full debt and every remaining lender is written down. · FP guard: safe if ids are minted monotonically and validated against a "created" flag, or if the counter is derived from an EnumerableSet length rather than hand-maintained.
- **Self-close: auction bought back into its own originating pool** — Trigger: `buyLoan(loanId, poolId)` / `refinance()` computes `oldPoolId` from the loan but never asserts `poolId != oldPoolId`. · Test: call with `poolId == oldPoolId`; then hand-compute the two pool-balance updates (debit `totalDebt`, credit `loan.debt + lenderInterest`) and check the net delta. · Impact: the pool is silently drained by the protocol-fee amount on every call, and `outstandingLoans` is inflated — repeatable, and it corrupts the pool's solvency accounting permanently. · FP guard: safe if the same-pool case is explicitly rejected, or if the two updates are provably idempotent on the same pool.
- **Refinance cancels an in-flight auction** — Trigger: refinance/migration path ends with `auctionStartTimestamp = type(uint256).max` (or equivalent "no auction" reset) and does not forbid refinancing a loan that is already in auction. · Test: start the auction, then have the borrower refinance into a different pool with identical terms and observe whether the auction still settles. · Impact: the borrower avoids seizure indefinitely by re-rolling the loan, pool balance falls by the protocol fee each cycle, and bad debt accumulates while the collateral is never recoverable. · FP guard: safe if refinancing an auctioned loan is blocked, or if the auction survives the refinance with its clock intact.
- **Minimum position size enforced only at creation** — Trigger: the minimum check appears in the open/create path only; `withdraw`, `reduceCollateral`, `repay`, and `liquidate` do not re-evaluate it. · Test: deposit the exact minimum, then withdraw to just under it, then borrow — check whether the position can be driven below the floor after it is open. · Impact: the floor is decorative; the entire dust class becomes reachable from an initially compliant position. · FP guard: safe if a single post-condition (`require(positionValue >= minValue)`) runs at the end of every mutating path, or if positions are rounded up to the floor on reduction.
- **Minimum-deposit sentinel disables the check** — Trigger: `if (minDepositEthValue == ONE_WEI) return true;` — a sentinel value that short-circuits the safety check rather than being rejected at configuration time. · Test: read the config setters and find every value that makes a check a no-op; confirm whether it is reachable via an admin setter with no lower bound. · Impact: governance (or a compromised admin) unknowingly converts a guarded protocol into an unguarded one; misconfiguration, not attack, but the loss is the same. · FP guard: safe if the sentinel is only settable before initialisation, or if the setter enforces a sane minimum.
- **Minimum collateral not re-checked after withdrawal** — Trigger: `checksWithdraw`/`withdraw` validates the *ratio* but not the resulting position value against the minimum. · Test: deposit the minimum, withdraw all but a dust amount, and check whether the minimum-position invariant still holds. · Impact: the cheapest dust-position factory on the protocol — a single deposit satisfies the gate for an unlimited number of sub-floor positions. · FP guard: safe if the minimum is expressed as a ratio rather than an absolute, or if the withdrawal path re-runs the open-time check.
- **Post-liquidation residue below the minimum is not reverted** — Trigger: `require(debtAfterLiquidation < minBorrowSize, "Must Liquidate All Debt")` — the comparison is written so a residual *under* the minimum satisfies it; classic sign error when debt is tracked as a negative balance (`.neg()`, `.sub()`). · Test: hand-evaluate the require with a partial repayment that leaves 30 against a minimum of 50, and check whether it reverts or passes. · Impact: partial liquidations always succeed while always leaving un-liquidatable dust; the debt is permanently uncollectible by design. · FP guard: safe if the residual is asserted `== 0` or `>= minBorrowSize`, and verify the intent in the revert string before flagging.
- **Position-size check placed before the realised amount is known** — Trigger: the dust/exit check uses a requested amount (`buyBackAmount`, `amountIn`, `debtToPay`) rather than the amount actually realised by the bid match. · Test: request a full exit in a market with insufficient depth so only part fills, and check whether the residue is still validated. · Impact: every partial fill leaves sub-minimum debt that no liquidator will touch; the check certifies the exit that didn't happen. · FP guard: safe if the check runs after the fill and reads the realised amount.
- **No buffer between borrow limit and liquidation threshold** — Trigger: borrow reverts on `newDebt > max` while the liquidation predicate is `debt < maxDebt → not liquidatable` — the same `max` on both sides. · Test: borrow exactly `max`, then move the oracle by one unit (or advance one block of interest) and check whether the position is immediately liquidatable. · Impact: an account can be liquidated in the same block it opens, before it can add collateral or repay; converts ordinary volatility into forced collateral sales. · FP guard: safe where the liquidation threshold is strictly below the borrow LTV (a real buffer, e.g. 80% borrow / 85% liquidate).
- **Boundary operator at the debt limit** — Trigger: `if (newDebt > max) revert` (strict) combined with `if (debt >= maxDebt)`-style liquidation, i.e. the maximum is *reachable* by borrowing and *sufficient* for liquidation. · Test: two-sided boundary test at exactly `max`, `max − 1`, `max + 1` for both the borrow and the liquidation predicate. · Impact: reachable-maximum positions are auto-liquidatable; same economic outcome as the missing buffer but far more likely to be missed in review because each individual check looks correct. · FP guard: only a false positive if the two predicates use different variables (e.g. one uses debt-with-accrued-interest).
- **Liquidation surcharge computed on pre-cap collateral** — Trigger: `collateralToLiquidate` is clamped with `if (collateralToLiquidate > accountCollateral) collateralToLiquidate = accountCollateral;` but the surcharge formula still uses `collateralToLiquidateWithoutDiscount` (the uncapped value). · Test: evaluate both formulas at a 99% price crash where `withoutDiscount × 10^decimals / price ≫ accountCollateral`, and check whether `collateralToLiquidate − surcharge` underflows. · Impact: the liquidator's payout underflows and reverts exactly when the position is most distressed — i.e. liquidation is impossible precisely in the scenario it exists for, converting the position into bad debt. · FP guard: safe if the surcharge is derived from the capped value or from `min(raw, capped)`; verify decimals before claiming the overflow.
- **Liquidation reachable but blocked by a protocol switch** — Trigger: `if (liquidationsLocked) revert;` or `if (block.timestamp - lastAuctionStart < liquidationAuctionMinSpacing) revert;` on the liquidation entrypoint, with the switch/admin under the same role that can also move collateral or pause. · Test: set the switch, advance time, and confirm every liquidation path (including the "seize on expiry" path) reverts; then check who can set it and whether there is an unset path. · Impact: one flag makes every distressed position unrecoverable — a single point of protocol-wide insolvency, and a cheap griefing vector if the role is not tightly held. · FP guard: safe if the lock is short-bounded, auto-expiring, or cannot be set while positions above a risk threshold are open.
- **Collateral valuation ignores interest accrued on the deposit** — Trigger: `pos.underlyingAmount += amount;` on deposit only, and the risk/health function values collateral as `price × underlyingAmount` while the interest-bearing share (`underlyingVaultShare`) is never used. · Test: let interest accrue for a full period (or warp a year) and compare the health computation against the true redeemable value of the position. · Impact: healthy positions are misvalued as risky and liquidated prematurely; the borrower loses the accrued yield *and* the collateral premium, and the liquidator takes a position that was never actually under-collateralised. · FP guard: safe if the risk path redeems/converts to the current share value, or if the deposit is non-yield-bearing by construction.
- **Unchecked subtraction on a user-supplied repayment** — Trigger: `unchecked { credit.principal -= principalPayment; }` with no `require(amount <= credit.principal + credit.interestAccrued)` upstream. · Test: repay 2× the outstanding debt and inspect the resulting principal — it wraps to ~2^256 instead of reverting or refunding. · Impact: the borrower self-destructs the position, or any third party griefs them into instant liquidatability for one transaction of capital; the over-payment is also irrecoverable. · FP guard: safe if the payment is clamped (`repayAmount = min(amount, owed)`) or the subtraction is checked; note some protocols *intend* over-repayment to revert.
- **Pool-accounting double-decrement on the refinance path** — Trigger: the same pool balance is reduced twice in one call — once through a helper (`_updatePoolBalance(poolId, pools[poolId].poolBalance - debt)`) and once inline (`pools[poolId].poolBalance -= debt;`). · Test: trace every `poolBalance` write in the function and cache the balance before/after in a unit test or by hand-summing the deltas. · Impact: the pool is debited twice for the same debt, permanently understating liquidity; lenders cannot withdraw and later borrowers are silently uncollateralised. · FP guard: safe if the two writes touch different pool ids, or if the inline write is over a `memory` local that never persists.
- **Multi-market liquidation loop mutates the collection it iterates** — Trigger: `for (i = 0; i < account.activeMarketsIds.length(); i++) { ...; account.updateActiveMarkets(id, ..., 0); }` where the update calls `EnumerableSet.remove()`. · Test: create positions in ≥3 markets (so a swap-and-pop reorders rather than truncates), liquidate, and check whether the loop indexes past the new length. · Impact: the account's liquidation reverts permanently — the largest, most systemically risky accounts are the ones that become un-liquidatable, which is the worst possible inversion of the incentive. · FP guard: safe if the loop caches ids into a memory array first, iterates downwards, or removes only after the loop; verify the set implementation actually does swap-and-pop.
- **Zero-liquidity collateral position bricks liquidation** — Trigger: collateral can be an LP/NFT position (`decreaseLiquidity`, `burn`) whose downstream callee enforces `require(params.liquidity > 0)`, and the deposit path never asserts `liquidity > 0`. · Test: deposit a position with `liquidity == 0`, make it under-collateralised, and confirm the liquidation call reverts in the unwrap step. · Impact: the borrower engineers a permanent, worthless-but-un-liquidatable position and escapes with the borrowed funds; every such position is pure protocol loss. · FP guard: safe if the deposit path rejects zero/negative-liquidity positions, or if the liquidation path has a fallback that seizes the position without unwrapping it.
- **Price-updater role revocable by anyone** — Trigger: `removeFeeder(x)` guarded by an existence modifier (`onlyWhenFeederExisted`) rather than an auth modifier (`onlyRole(DEFAULT_ADMIN_ROLE)`), where the price getter reverts on staleness. · Test: from an unprivileged account, revoke the last feeder, let the price age past `expirationPeriod`, and attempt a liquidation. · Impact: a borrower one step from liquidation removes the only price source and makes their position permanently un-liquidatable — the direct path from "distressed" to "bad debt written off by lenders". · FP guard: safe if the price does not hard-revert on staleness (falls back to a secondary source or a last-known-good with a bound) — check the getter, not just the setter.
- **Liquidation depends on an external call that reverts for some variants** — Trigger: a guard/context check whose whole job is to exercise an external protocol — e.g. `ICurve2TokenPool(pool).remove_liquidity(0, minAmounts)` — used to gate liquidation. · Test: enumerate the concrete pools/implementations actually registered and run the guard call with zero values against each; look for implementations that underflow on a no-op call. · Impact: liquidation is impossible for the affected pools; the vulnerable borrower escapes entirely and the loss lands on the protocol. · FP guard: often a false positive if only one implementation is ever registered — verify the registry's contents and whether the pool address is admin-settable to an arbitrary implementation.
- **Ratio invariant evaluated inside the accumulator loop** — Trigger: `require(uint256(assetIn) * due.collateral >= uint256(collateralOut) * due.debt)` placed *before* `assetIn += param.assetsIn[i]`, so both accumulators are still zero on the first iteration. · Test: call with `assetsIn[0] = 0` and `collateralsOut[0] = full`, and evaluate the require by hand; `0 * c >= 0 * d` is true. · Impact: the entire collateral is withdrawn against zero repayment in one call; the loan record's debt is untouched and the pool is short the full principal. · FP guard: safe if the invariant is evaluated once on the aggregate after the loop, or uses per-entry amounts rather than accumulators — and a zero-amount guard alone does not fix it, both arrays can be non-trivially populated.
- **Allowlist gates repayment but not liquidation** — Trigger: `repay()` carries `onlyWhitelistedToken(token)` while `liquidate()` — which internally routes through the same repayment logic — does not. · Test: remove a token from the allowlist, then confirm repayment reverts while liquidating a position that borrowed that token still succeeds. · Impact: borrowers holding a de-listed asset cannot defend their position but can still be liquidated; a governance action converts into forced loss of collateral, and the asymmetry is a griefer's lever if the de-list path is cheap. · FP guard: safe if de-listing is scoped to *new* loans only and existing positions are explicitly exempted in both paths.
- **Pause flag gates repayment but not liquidation** — Trigger: `repay()` begins `if (!isRepayAllowed()) revert REPAY_NOT_ALLOWED();` and `liquidate()` touches the same state without that check. · Test: flip the flag off; confirm repay reverts and liquidate succeeds; then confirm nothing re-gates liquidation on resume. · Impact: the protocol can unilaterally prevent every borrower from reducing debt while liquidators keep operating — positions that drifted during the pause are force-closed the moment it lifts, with no window to act. · FP guard: safe if the pause is scoped to *new* borrowing only, or if liquidation carries an equivalent or stronger gate.
- **Pause blocks the user's remedy but not liquidation** — Trigger: the pause/frozen flag is checked in `close`, `repay`, `depositCollateral`, and `increaseCollateral` but not in the liquidation entrypoint (or vice versa). · Test: pause, move price against a position, unpause, and check whether liquidation can execute before the borrower's first possible defence transaction (compare ordering in the same block). · Impact: the borrower absorbs market moves they are forbidden from reacting to, and liquidation bots capture the difference; repeatable at every pause, and the protocol looks complicit. · FP guard: safe if a grace period of ≥ the pause length (capped) delays liquidations after resume — verify the delay exists in code, not in docs.
- **Collateral pause blocks both close and liquidation** — Trigger: `collateralValid[addr] = false` (or `paused = true`) is read by both `closeLoan` and `callLiquidation`, so pausing a collateral type short-circuits every exit. · Test: pause a collateral type while loans against it are open and try to (a) repay-and-close, (b) liquidate a now-underwater position. · Impact: borrowers are locked out of their own collateral and the protocol accumulates loans that can never be resolved either way — a permanent, governance-triggered bad-debt hole. · FP guard: safe if pause only blocks *new* deposits/loans and explicitly exempts close and liquidation.
- **Liquidation path with no token transfer bypasses a frozen collateral token** — Trigger: the liquidation branch only adjusts internal accounting (`values.pnlAmountForPool = collateralAmount - fundingFee`) while close/add-collateral perform `safeTransferFrom`. · Test: pause the collateral token, then check which of {close, addCollateral, liquidate} revert: if the first two revert and liquidation does not, users cannot defend while the system disposes of them. · Impact: forced liquidation of positions the owner had no ability to save, and the accounting change may not even reflect a real transfer — double-counting risk on top. · FP guard: only a false positive if the collateral is provably held in an address that the pause does not affect, or if a separate, unpaused exit path exists for users.
- **Live price feed demanded where no valuation is needed** — Trigger: a shared `_checkIfCollateralIsActive`/stale-price/circuit-breaker check applied unconditionally at the top of functions that only *reduce* risk (closing a fully-repaid loan, adding collateral). · Test: trip the stale-price flag, then attempt to fully repay and to add collateral; both should be safe actions and should not require a fresh price. · Impact: users are trapped with accruing interest while a market-wide stale-price condition persists, and can be liquidated for positions they were trying to fix. · FP guard: safe if the check is conditional on remaining debt (`if (outstanding > threshold)`), which is the correct fix — diff the branch, not the call site.
- **Adding collateral requires meeting the liquidation threshold** — Trigger: `increaseCollateralAmount` recomputes `colInUSD >= borrowMargin` and reverts when stale prices make the comparison fail, even though adding collateral strictly improves the ratio. · Test: with a stale or depressed price, attempt to add collateral to an underwater position. · Impact: the single action that could rescue a position is the one most likely to be blocked, converting recoverable positions into liquidations and losses for both sides. · FP guard: safe if the check is a no-op when the added amount is positive, or is skipped entirely on the add path.
- **Public function mutating collateral/lien records with no authorisation** — Trigger: `function _deleteLienPosition(uint256 collateralId, uint256 position) public` — an `_`-prefixed internal-looking helper exposed as `public`, with no modifier. · Test: list every `public`/`external` function that writes a collateral, lien, share, or position record, and check each for a modifier or an explicit `msg.sender` assertion. · Impact: any third party removes a lender's security interest and the borrower then withdraws the now-unencumbered collateral — the lender's entire claim is destroyed for gas. · FP guard: safe if the caller's ownership of the affected record is asserted inside the body, or if an internal entrypoint with the public one only called from authorised paths exists.
- **Index-based reference into an array that shifts on removal** — Trigger: a removal helper that does `for (i = position; i < stack.length - 1; i++) stack[i] = stack[i+1]; stack.pop();` while other records store `position` as an index into that array. · Test: remove an element below a stored index, then resolve the stored index and check whether it still points to the same logical lien. · Impact: collateral/lien references silently rebind to the wrong record — a lender can be made to release the wrong collateral, or a borrower's debt binds to someone else's lien; the corruption is permanent. · FP guard: safe if references are keyed by id rather than array index, or if a swap-and-pop with an explicit index-fixup is used (check the fixup actually updates the *stored* index of the moved element).
- **Unbounded rollover extends the loan indefinitely** — Trigger: `roll()` adds `req.duration` to `loan.expiry`, increases debt and collateral, and has no counter; `loan.rollable` defaults to true. · Test: call roll repeatedly in one transaction (or N sequential ones) up to expiry and check whether any ceiling exists, including whether the lender can effectively disable it. · Impact: the borrower renews forever and the lender's principal is never recoverable — the position is nominally alive and never liquidatable, so it becomes a permanent write-off that a rational borrower will always take. · FP guard: safe if a max-rolls counter, an aggregate time cap, or a lender-side toggle with an effective default-off is enforced on-chain.
- **Role/parameter revocation missing a range or ownership check** — Trigger: a keeper/admin-supplied scalar is used as a multiplier without a bound — `_withholdTau((tauReturned * _rewardProportion) / PERCENT_PRECISION)` with no `require(_rewardProportion <= PERCENT_PRECISION)`. · Test: pass a value above the denominator (e.g. `2e18` against `1e18`) and check whether the withheld amount exceeds the amount actually received. · Impact: a single privileged call accounts for more value than exists, wiping out the bad-debt buffer and letting borrowers withdraw collateral against unpaid debt — an instant protocol-wide solvency break. · FP guard: safe if the parameter is range-checked at the setter *and* at the use site, or if the resulting value is clamped to the available balance.
- **Market can be disabled while positions are open, and liquidation still runs** — Trigger: `updatePerpMarketStatus`/`setMarketActive(false)` with no `require(openPositions == 0)`, while the close path reverts on a disabled market and the liquidation path does not. · Test: open a position, disable the market, then attempt (a) close, (b) liquidation after a price move — confirm the asymmetry. · Impact: traders are locked into positions they can only lose on; the operator's switch becomes a mechanism for converting user equity into liquidation fees, and the same switch is a censorship vector. · FP guard: safe if closing/reducing is explicitly exempted on a disabled market, or if disabling requires zero open interest or a timelock.
- **Sentinel `type(uint256).max` overloaded as "unset"** — Trigger: `loan.auctionStartTimestamp = type(uint256).max` means "no auction", and a comparison against it (`> loan.auctionStartTimestamp + loan.auctionLength`) is the only auction-state test. · Test: find every arithmetic or comparison use of the sentinel; look for `block.timestamp > MAX + length` overflow behaviour and for state transitions that fail to restore or clear the sentinel. · Impact: one missed reset leaves a loan permanently in or out of auction, so liquidators are refused (bad debt) or the loan is auctioned again after settlement (double-sale of the same collateral). · FP guard: safe if the sentinel is never compared arithmetically (a dedicated `bool inAuction` is the correct pattern) — flag the arithmetic use, not the sentinel itself.
- **Liquidation timing computed from acceptance rather than next payment due** — Trigger: `canLiquidate` compares `block.timestamp - lastRepaidTimestamp(loan) > paymentDefaultDuration` and `lastRepaidTimestamp()` falls back to `loan.acceptedTimestamp` when unset — with no `paymentCycleDuration` in the expression, and no enforced `paymentDefaultDuration >= paymentCycleDuration`. · Test: open a loan where the first payment falls due in 30 days and the grace period is 7, then advance 8 days and evaluate the predicate. · Impact: a borrower in good standing on day 8 of a 30-day cycle has collateral worth far more than the debt seized by any liquidator — pure theft of the borrower's equity, reproducible on every loan. · FP guard: safe if the predicate is `block.timestamp > nextDueDate + defaultDuration` where `nextDueDate = accepted + n * cycle`; check the config relationship before flagging, since `defaultDuration < cycleDuration` is the actual defect.
- **Health-factor improvement not enforced after liquidation** — Trigger: the liquidation body has `if (startingUserHealthFactor >= MIN_HEALTH_FACTOR) revert` and/or no `if (endingHealthFactor <= startingHealthFactor) revert`. · Test: liquidate a position and recompute the health factor from the post-state; check that it strictly improved and that the pre-state was genuinely below the threshold. · Impact: repeated or oversized liquidations that leave the position worse convert a recoverable position into a guaranteed shortfall, and a borrower can self-liquidate to extract the bonus repeatedly. · FP guard: safe where the health factor is provably monotonic in the repaid amount and the entry gate is a strict inequality against the same threshold the bonus uses.
- **Net-negative liquidation economics for ordinary positions** — Trigger: `liquidationBonusPct` (or `LIQUIDATION_BONUS`) is close to or below `liquidationFee + protocolFee`, and the gas cost is not accounted for anywhere in sizing the bonus. · Test: compute, for a median position size on the target chain, `collateralSeized × bonus − fees − gas`; if ≤ 0 the position is never liquidated by a rational actor. · Impact: the protocol's core safety mechanism is inoperative at the sizes it actually holds; the only liquidator is the protocol itself (or nobody), and under-collateralised debt is not cleared. · FP guard: safe where a permissionless keeper is subsidised, where the protocol self-liquidates with its own capital, or where positions are provably large enough that the margin is robust across gas regimes — quantify before flagging.
- **Non-existent id accepted by a claim/withdraw path** — Trigger: `reclaimContract` / `repay` / `withdraw` derives an id from user input (`uint(orderHash)`) and checks expiry, settled and reclaimed flags but never that the order was ever matched or the id ever created. · Test: craft an order that was never matched, satisfy the three flag checks, and confirm the payout branch executes. · Impact: funds are released against a fabricated instrument — the payout is real value leaving the contract for a position that was never collateralised. · FP guard: safe if the id is validated against a registry populated only on a real match (`require(matchedOrders[id].maker != address(0))`) — verify the registry is written on the legit path.
- **Missing zero-address validation on a payout recipient** — Trigger: `address recipient = registry[id];` followed by `IERC20(asset).safeTransfer(recipient, amount)` with no `require(recipient != address(0))`, where `registry[id]` is unset for a path the caller can construct. · Test: reach the payout with an id that was never registered and confirm the transfer targets `address(0)`; note `safeTransfer` does *not* protect against a zero recipient. · Impact: the payout is permanently burnt — an unrecoverable loss for the counterparty, triggered by attacker-supplied input at gas cost only. · FP guard: safe if the registry is guaranteed populated before the branch is reachable, or if the transfer helper rejects zero recipients — check the actual token behaviour, since many do not revert.

## Sequence

Run in this order — each pass assumes the previous one has established the frame:

1. **Frame the economics first.** Total value at risk, the liquidation bonus percentage, the liquidation fee, and the realised gas cost on the target chain. Compute `liquidatorProfit = seizedCollateralValue × bonusPct − protocolFee − gasCost` at the protocol's own minimum position size. If that number is ≤ 0, the whole dust/liquidation-incentive family (entries 1, 10–14, 42) is live and becomes the highest-yield thread. Do this before reading any code — it tells you whether the protocol's safety mechanism can even fire.
2. **Draw the lifecycle state machine on paper.** open → accrue → repay/refinance → auction/liquidate → write-off → close. Then, for each transition, list every function that can perform it. This is the artifact that makes the pause-asymmetry, allowlist-asymmetry, sentinel, and write-off checks mechanical (entries 18, 26–32, 36, 38–39).
3. **Enumerate the entrypoints and gate each one.** For every `external`/`public` function: who can call it, what state it writes, and whether a modifier checks *authorisation* or merely *existence*. Then build the gate matrix — rows are entrypoints, columns are the protocol's global flags (paused, frozen, allowlisted, disabled, stale-price, liquidationsLocked) — and look for rows that are empty where their siblings are not. This one table produces the entire asymmetric-gating family (entries 26–33, and 34 for pure visibility).
4. **Read every parameter mutator, and diff its guard against its parameter struct.** For each `update*`/`set*` function, tabulate which fields it can change and which fields the invariant actually constrains. Any field in column A but not column B is a candidate; the oracle/price-source field is the one that pays (entry 3).
5. **Grep the state-lifecycle primitives.** `delete ` (then check every later use in the same body), raw `mapping[key]` reads with no existence sentinel, hand-maintained counters decremented on unvalidated input, `type(uint256).max` as a sentinel, and any array removal followed by index use. Five greps, and they are near-deterministic — entries 6, 7, 35, 39, 43.
6. **Walk the liquidation entrypoint line by line with the attacker's wallet open.** What inputs are attacker-controlled (entry 2), which stored values are re-derived from inputs, is the collateral amount clamped anywhere and if so is the *fee* computed on the clamped or unclamped value (entry 17), and what is the dividend/divisor of every ratio (entries 4, 15, 16). Then ask who can be liquidated *first* — the newest, largest position.
7. **Trace every loop that mutates its own collection or evaluates an invariant mid-accumulation.** For each: cache the iterated collection into memory, confirm the removal semantics of the container, and hand-evaluate the invariant on the first iteration with zeroed accumulators (entries 22, 26).
8. **Follow the external calls.** Every call to a Uniswap/Balancer/Curve/router/position-manager/registry from a liquidation, valuation, or guard path: which concrete implementations are registered, do they revert on zero/edge inputs, and does the wrapper use `safeIncreaseAllowance` against a token that already returns `type(uint256).max` (entry 25).
9. **Timing and accrual last.** Compare every duration constant to the period it should relate to (`paymentDefaultDuration` vs `paymentCycleDuration`, `expirationPeriod` vs feed cadence), confirm interest accrues into the value used by the health check, and check that schedule variables advance by a fixed interval rather than being reset to `block.timestamp` (entries 19, 40).
10. **For each finding that survives, write the falsifier before writing it up.** A number, an assertion, or a one-line test that would prove it wrong. If none can be written, it is a heuristic candidate, not a finding — park it.
