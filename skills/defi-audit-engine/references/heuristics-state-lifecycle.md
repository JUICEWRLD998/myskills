**Scope:** state-lifecycle bugs — records that are created, mutated, deleted, reset, or left half-initialised, and the code that reads them. Covers the *mechanism* layer shared by lending, perps, auctions, and any mapping/struct bookkeeping: use-after-delete, mapping-default-accepted-as-valid, counters driven by unvalidated input, unset sentinels, uninitialised structs passing guards, state read after a reset, and existence-checks standing in for authorisation. Ordered by expected yield. Derived from `Lending/invalid-Address/`, `Lending/withdraw-issues/`, `Lending/Debt/`, `Lending/Liquidation-issues/{Cant-be-Liquidated,Loan-writeoff,prevent-Liquidation}/`, `Lending/grief-auction/`, and the deleted-state and default-value triggers in `General-Checklis.md`.

- **State deleted, then read again in the same function** — Trigger: `if (repaid == loan.amount) delete loans[loanID];` followed later in the same body by a read of a member of that record (`debt.transferFrom(msg.sender, loan.lender, repaid)`). · Test: grep every `delete <mapping>[key]` / `.pop()` / `= Record()` assignment, then list every later use in the same function body — a `storage` pointer read after the delete returns the type's zero value, not the old one. · Impact: the payout is addressed to `address(0)`. Tokens that revert on a zero recipient make the function unusable; tokens that accept it burn the value permanently, so the counterparty's full claim disappears in one transaction with no recovery path. · FP guard: safe if the deleted object was a `memory` copy, if the delete is the last statement before a `return`, or if the value was cached into a local before the delete — the bug requires the read to go through the storage reference, so check the declaration, not the call site.

- **Field-by-field "reset" that leaves a zombie record** — Trigger: a close/liquidate/write-off path zeroes some fields (`principal = 0`, `debt = 0`, `status = CLOSED`) but omits others (`lender`, `collateral`, a timestamp, a share), or deletes one mapping entry while a parallel index still references the id. · Test: after the terminal operation, dump every field of the record and every other structure keyed by the same id; anything still non-zero that another function reads is a zombie. · Impact: the partially-reset record is still live to whoever reads the surviving fields — the classic outcome is a claim paid twice (collateral released, then released again from the stale field) or a position that counts toward a global total it no longer represents. · FP guard: safe if the terminal path is a single `delete` of the whole struct plus every index, or if all readers gate on the status flag first — check every reader before claiming the zombie is reachable.

- **Mapping default accepted as valid — no existence sentinel** — Trigger: `Record memory r = records[id];` with no `require(r.exists)`, no `createdAt != 0` check, and no separate boolean map; the guards that follow (`if (r.amount > 0) revert`) are all satisfied by an all-zero struct. · Test: call every id-taking function with an id that was never created and follow execution to see which branch it reaches and what it writes; a `mapping` read never reverts, so the compiler offers no help here. · Impact: fabricated or uninitialised ids drive real state transitions — payouts released against instruments that never existed, records "closed" that were never opened, and shared counters walked down to a terminal state that unlocks something global. · FP guard: safe if ids are minted monotonically from a counter that cannot be guessed and every read is preceded by a membership check in a set that is written on creation — verify the *creation* path populates the sentinel before trusting the guard.

- **Non-existent id accepted by a claim, reclaim, or repay path** — Trigger: an id derived from caller input (`uint(orderHash)`, a user-supplied `loanId`) is checked against flags (`isExpired`, `settled`, `reclaimed`) but never against "this thing was ever registered". · Test: construct an input that satisfies all the flag checks while no record exists; check whether the payout branch executes and whether the flags themselves are read from the same defaulted struct. · Impact: real value leaves the contract against a fabricated instrument — the flags all read as "not yet claimed", which is exactly the state a fake id occupies, so the attacker's cost is gas and the loss is whatever the payout is. · FP guard: safe if the id is validated against a registry written only on the legitimate match path (`require(matched[id].maker != address(0))`) — confirm that registry is actually populated before the branch is reachable.

- **Shared counter decremented on an unvalidated input** — Trigger: `unchecked { --count; }` (or `count -= 1`) inside a function that can be called with an id that does not correspond to a live record. · Test: call the function N times with non-existent ids, where N is the current `count`, and observe the global status flag or the operation the counter gates. · Impact: the counter is a proxy for "how much real exposure remains", so walking it to zero flips a facility-wide status (e.g. `REPAID`) while nothing was repaid — every subsequent calculation that trusts the status is wrong, and the remaining counterparties are written down. · FP guard: safe if the decrement is guarded by an existence check on the same id, or if the counter is derived from a collection's length rather than hand-maintained — a `require(count > 0)` alone does not fix it.

- **Hand-maintained counter that can disagree with the collection it summarises** — Trigger: a `count`/`openPositions`/`totalLoans` variable updated by hand on each mutation instead of being derived (`ids.length()`) or bounded by the collection. · Test: drive the collection through create/delete/re-create sequences and compare the counter against `length()` at each step; look for any path that writes the collection without touching the counter, or vice versa. · Impact: every guard written as `count == 0` / `count > 0` becomes unreliable — the terminal-state transitions they protect fire early or never, so the operation either reports success while exposure is open or refuses to ever complete. · FP guard: safe if every write to the collection is in the same function as the counter update and no path returns early between them — the early-return-between-the-two is the most common way this is a real bug and the least common way it gets spotted.

- **Reset value that must be cleared is left carrying a previous cycle's value** — Trigger: a full write-off / full repayment / full close that sets the principal or balance to zero but does not reset the associated timestamp (`accountBorrows[borrower].lastRepay` stays at the old block). · Test: borrow, fully write off, borrow again at a later block, then evaluate the overdue/eligibility predicate that reads the timestamp; the library's own trace of this shows the second loan being treated as if it were taken at the first loan's block. · Impact: the stale timestamp makes a brand-new position immediately eligible for whatever the timestamp gates — in the source instance, anyone could instantly write off a fresh loan, so the guarantor/lender covers a debt that was never overdue, repeatably, for gas. · FP guard: safe if every path that zeroes the amount also zeroes or advances the timestamp, or if the predicate reads a per-cycle field that is re-initialised on open — check the *reborrow* path specifically, since the bug is invisible on a single cycle.

- **Unset sentinel overloaded as a state marker and used in arithmetic** — Trigger: `field = type(uint256).max` meaning "no event scheduled", combined with comparisons like `block.timestamp > field + length` or restored by `field = type(uint256).max` in the terminal path. · Test: enumerate every read of the sentinel and classify each as equality (`== MAX`, safe) or arithmetic (add/compare, unsafe); then verify every transition restores the sentinel on the terminal path. · Impact: two distinct failures — arithmetic on the sentinel mis-evaluates the state test (an event is considered live or dead for the wrong reason, so auctions are refused or re-run against already-settled collateral), and a missed restore leaves the record permanently in the wrong state. The second-order effect is a double-settlement: the same collateral sold twice. · FP guard: safe if the state is a dedicated `bool`/enum and the sentinel is only ever compared for equality — flag the arithmetic use and the missing restore, not the sentinel's existence.

- **Uninitialised struct passes every guard** — Trigger: a struct pulled from storage or declared `memory` and used without a single field being asserted non-zero, then written back (`tokenLoanParams[id] = params;`, `config[asset] = cfg;`). · Test: for every struct write, check whether at least one field of the assigned value is validated; for every struct read, check whether the guards would pass on an all-zero value. · Impact: a zero-valued configuration becomes operational — a zero fee, a zero oracle address, a zero limit, or a zero LTV all read as "configuration present" and propagate silently, and the failure is discovered only when the derived behaviour is wrong (free borrowing, a call to `address(0)`). · FP guard: safe if the struct has an explicit `initialised`/`version` field that is always checked, or if all fields are validated at the setter — a struct that is *always* fully populated on every reachable path clears this, so check the setter before the reader.

- **First-write / initialisation path missing, so operating defaults are `address(0)` or `0`** — Trigger: a registry lookup (`bulls[contractId]`, `oracles[asset]`, `feeReceivers[kind]`) that is only populated on one path, but read on others with no `!= address(0)` guard. · Test: for each registry, enumerate the writers and then enumerate every reader; any reader reachable before the writer has run is a finding. · Impact: the operation proceeds with a zero-address counterparty or a zero limit — value sent to `address(0)` is burnt, and a zero limit silently disables the check it was supposed to enforce, which reads as a working system. · FP guard: safe if the read paths are strictly ordered after the writes (initialisation is guaranteed by construction, e.g. both happen in the same transaction) — verify the ordering rather than assuming the deployment sequence covers it.

- **Existence check where an authorisation check is required** — Trigger: a modifier named for permission (`onlyWhenFeederExisted`, `isProduct`, `validToken`) whose body only tests presence in a set or mapping, with no `msg.sender`/role assertion. · Test: for each modifier, read its body and classify it: presence vs permission. Then call the guarded function from an unprivileged account and see whether the modifier passes. · Impact: any account can perform a privileged action that the modifier appears to protect — in the source instance anyone can revoke the price-updater role, which makes the price stale, which makes every price-dependent action revert; the same shape applied to a fund-moving function is direct theft. · FP guard: safe if a second modifier on the same function carries the role check, or if the body asserts `msg.sender` membership — read both modifiers before flagging, but note that relying on a second modifier to carry the security property is itself fragile.

- **Role revocation reachable by the wrong party** — Trigger: `revokeRole`/`_removeFeeder`/`removeOperator` invoked from an entrypoint whose guard is weaker than the granting path's guard. · Test: build the role matrix — for each role, who can grant it and who can revoke it — and look for revoked-by-anyone where granted-by-admin. · Impact: the grant path is protected and the revoke path is not, so the asymmetry is invisible in review; the effect is a denial of service on whatever the role enables (price updates, keeper actions, liquidations) and it can be triggered by the party most motivated to stop that function. · FP guard: safe if revocation is deliberately permissionless (a public "remove a malicious operator" design) — check whether the intended design is documented, and note that even an intentional design here is a liveness risk if the role is load-bearing.

- **Sensitive record mutated by a `public` function with no authorisation** — Trigger: `function _deleteLienPosition(uint256 collateralId, uint256 position) public` — an `_`-prefixed internal-looking helper exposed publicly, mutating collateral/lien/share records. · Test: list every `public`/`external` function that writes a security-interest, share, or ownership record, and check each for a modifier or an explicit `msg.sender` assertion. · Impact: any third party removes another party's claim on an asset, after which the owner withdraws the now-unencumbered collateral — the lender's entire claim is destroyed for gas, and the withdrawal is legitimate from the contract's point of view. · FP guard: safe if the body asserts the caller's ownership of the affected record, or if the function is only reachable from guarded callers despite its visibility — check for an internal wrapper with the external name, since the visibility is sometimes intentionally wide.

- **State read after a cross-module reset** — Trigger: module A deletes or flags a record; module B (or a later function) reads a *different* field of the same record, or a cached copy taken before the reset, without re-checking the status. · Test: for each delete/reset site, search the whole codebase for readers of every field of that record and for cached locals that outlive the reset. · Impact: the reset is observed by some readers and not others, so the system operates on two inconsistent views of the same position — one module pays out while another still counts the exposure, producing either double-payment or phantom debts. · FP guard: safe if all readers gate on a single status field that the reset always writes first, and no cached copy crosses the reset — trace the cache lifetime, since an in-function local is fine and a storage cache in another module is not.

- **Payout recipient never validated against the zero address** — Trigger: `address to = registry[id];` or `loan.lender` used directly in `safeTransfer(to, amount)` with no `require(to != address(0))`. · Test: reach the payout with each id whose recipient slot is unset and confirm the transfer target; check the token's actual behaviour for a zero recipient rather than assuming it reverts. · Impact: the value is burnt irrecoverably. The distinguishing feature is that `safeTransfer` does not help here — the safety wrapper guards the return value, not the recipient — so teams that "fixed" the ERC20 issue still carry this one. · FP guard: safe if the recipient is proven non-zero by construction (set in the same transaction from `msg.sender`) or if the recipient is validated at the writer — the finding requires a reachable path where the slot is still zero, so enumerate the writers first.

- **Repeated deletion or closure of the same record** — Trigger: a close/cancel/claim function with no `require(status != CLOSED)` and no deletion-ordering assumption that would fail on a second call. · Test: call the terminal function twice on the same id and diff the state; if the second call succeeds, check what it charged, paid out, or decremented. · Impact: repetition compounds whatever the function writes — a counter walks further than it should, a refund or bonus is paid twice, or a global flag flips to a state the first call was already at the boundary of. This is the cheapest class of bug to execute and to miss. · FP guard: safe if the write is idempotent by construction (assigning a value rather than accumulating), or if a status flag is moved before the effect and re-checked — an accumulating side effect with no guard is the finding.

- **Deletion that leaves a ghost entry in the enumeration** — Trigger: a record is removed from a mapping but not from the set/array used to iterate over records, or vice versa; `EnumerableSet.remove` is skipped while the mapping entry is deleted. · Test: after every delete, iterate the enumeration and resolve each key in the mapping; an id that resolves to a defaulted record is a ghost. · Impact: every loop over the enumeration now processes a non-existent entity — the effect ranges from wasted gas to a revert that blocks the whole operation (the classic outcome being an account whose liquidation loop fails permanently), and the ghosts accumulate with each delete. · FP guard: safe if the delete is a single helper that removes from both structures atomically, or if the iterating code skips defaulted records — check the helper rather than each call site, since a partial helper is the root cause.

- **Terminal state that is never reachable, so the record is perpetual** — Trigger: an extension/rollover/renewal path with no counter, no aggregate time cap, and no effective way for the counterparty to disable it (`loan.rollable` defaulting true). · Test: call the extension repeatedly — in one transaction if the function is callable twice, otherwise sequentially — and check whether any ceiling exists, including whether the counterparty can turn it off before the position is taken. · Impact: the position never reaches a terminal state, so the counterparty's principal is never recoverable and the record never leaves the book; a rational holder always extends, making the non-performing exposure permanent rather than transient. · FP guard: safe if a max-count, aggregate duration cap, or counterparty-side toggle with an effective default-off is enforced on-chain — a toggle that the borrower sets at open time is not a defence.

## Sequence

1. **Enumerate every record type and draw its lifecycle as a state machine.** For each struct/mapping: creation, mutation, and every delete/reset site. Then place each *reader* on the diagram. The whole class becomes mechanical once both lists exist, and two of the highest-yield entries (use-after-delete, cross-module reset) are only visible on this diagram.
2. **Grep the four primitives.** `delete `, `.pop()`, `= Record()`/`= 0` resets, and hand-maintained counters. For each hit, list every later use of that record in the same function — this is the highest-signal, lowest-effort pass in the whole checklist.
3. **For every id-taking function, call it with an id that was never created.** Trace which branch executes and what it writes. Do this before reading the guards: the point is to find out empirically whether the default struct satisfies them.
4. **Diff every writer's fields against every reader's fields, per record.** Columns: writer → fields written. Rows: reader → fields read. Anything read but not written on an early path is an uninitialised-default finding; anything written on the terminal path but not on the creation path is a zombie finding.
5. **Audit the terminal paths in detail** — the functions that delete, close, write off, or cancel. For each: is every field reset, is every index cleaned, is the sentinel restored, is every timestamp advanced or cleared, and is the function idempotent? Then re-run it twice and diff.
6. **Classify every modifier as existence-check or authorisation-check.** Read the body, not the name. Then list all callers of each guarded function and ask what an unprivileged caller can achieve.
7. **Walk the sentinel values.** For each `type(uintX).max` / `0` / `address(0)` used as a marker: list the readers, and split them into equality comparisons (safe) and arithmetic or dereferences (candidates).
8. **For each finding that survives, write the falsifier before writing it up** — a specific id, a call sequence, or an assertion that would fail. If none can be written, it is a heuristic candidate, not a finding.
