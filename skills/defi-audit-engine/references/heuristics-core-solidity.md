**Scope:** general Solidity review. Ordered by expected yield. Derived from `BEEDLE/` (rounding, slippage, stuck funds, unsafe transfer/ERC20 quirks, ownership transfer, MEV, pool balance), `General-Checklis.md`, `EXPLOITS-UniswapV3/`, and the non-price-adapter findings from `PLAZA-FINACE/`. - **Fee, interest or share truncates to zero on a large constant denominator** — Trigger: `a * scale / D` where `D` is a large constant (`1e18`, `10000`, `365 days`) and `a` is derived from user-controlled amounts; the tell is a scaling factor multiplied in specifically to preserve precision before the division. · Test: for each such expression, fuzz `a` across `1 … D/scale` and assert the result is never silently 0 — or solve the inequality by hand and state the smallest `a` at which the output first becomes nonzero. · Impact: the fee/interest/share is charged as zero while the position is still mutated as if it were charged; small positions therefore accrue free debt, pay no protocol fee, or receive no share — each instance is a per-position leak that scales with volume rather than a one-off loss. · FP guard: safe if the numerator is proven bounded below (`require(a >= minValue)`), if the truncation always lands in the protocol's favour, or if the denominator is small enough that the unit of truncation is economically irrelevant — state the largest tolerated rounding loss in token units before flagging.

- **Compounded truncation from chained divisions** — Trigger: `interest = (rate * debt * timeElapsed) / 10000 / 365 days` — two successive integer divisions rather than one combined denominator. · Test: evaluate the expression with realistic values and compare against the mathematically exact result computed at higher precision; report the relative error. · Impact: each division discards a fraction, so the effective rate is systematically lower than the configured rate — borrowers underpay interest, lenders and the protocol are short, and the error is proportional to volume so it compounds across the whole book. · FP guard: safe when the divisor chain provably cannot truncate (e.g. the product is always a multiple of the first divisor), or when the deviation is bounded by a dust threshold the protocol has explicitly accepted; do not flag a deliberate round-down that always favours the protocol.

- **Fee computed on a remainder that can be zero** — Trigger: `fee = (feeBps * (amountA - amountB)) / 10000` where `amountA - amountB` is a difference that can legitimately be 0 or 1 — e.g. a refinance fee on the *reduction* in debt. · Test: construct the case where the two amounts are equal or differ by one unit and check whether the fee is zero while the operation still succeeds. · Impact: the fee is bypassable by sizing the transaction so the remainder rounds to zero — an unlimited, repeatable fee leak rather than a rounding curiosity. · FP guard: safe if the difference is proven to exceed `10000 / feeBps` on every path, or if a minimum fee floor is applied; check whether a zero fee is actually reachable by a user-controlled input before flagging.

- **Rounding direction not pinned to favour the protocol** — Trigger: shares or assets computed with `/` in both the mint and the redeem direction, or the same expression reused for both. · Test: for each pair of inverse functions (deposit/withdraw, mint/redeem, borrow/repay), evaluate both at 1-unit amounts and check which side absorbs the truncation. · Impact: whichever side rounds down loses value on every round trip; a user who can loop the pair extracts a unit of value per iteration, and at 1-wei granularity the extraction is unbounded relative to the position. · FP guard: safe if mint rounds down and redeem rounds down (both in the protocol's favour), or if a minimum-share/min-amount guard prevents the 1-unit case; the direction, not the existence, of truncation is the finding.

- **Swap minimum-out set to zero or left unset** — Trigger: an external route/swap call whose minimum-output field is a literal `0`, a hardcoded constant, or absent from the function signature — `amountOutMinimum: 0`, `minAmountsOut` all-zero, no `minOut` parameter. · Test: read the call site and determine where the minimum-out value comes from; if it is not a caller-supplied parameter or an oracle-bounded computation, it is unprotected. · Impact: the swap executes at any price, so the full slippage budget is extractable by a sandwich on every call — a MEV bot's profit equals the price impact it can induce, drained directly from the protocol's or the user's proceeds. · FP guard: safe if a minimum out is derived from an on-chain oracle with a tolerance band (and the band is itself bounded), or if the swap amount is provably too small to be worth sandwiching — quantify the extractable value before flagging.

- **Deadline set to the current timestamp** — Trigger: `deadline: block.timestamp` in a swap/route call — the field exists but is meaningless because it can never be in the past relative to execution. · Test: grep every `deadline` argument and check whether it originates from a caller-supplied parameter or from `block.timestamp`. · Impact: the transaction is valid for any inclusion time, so a validator or builder can hold and land it at the most favourable moment, and the "short window" the deadline was meant to enforce does not exist — the protection is nominal, not partial. · FP guard: this is a low-severity/informational finding when the call has no other slippage protection either (the deadline was never the real defence) — pair it with a concrete extraction path or downgrade it.

- **Deadline not caller-controllable at all** — Trigger: the swap wrapper takes no deadline parameter, so the protocol's users cannot express an expiry. · Test: read the wrapper's signature; if there is no way for the caller to pass a deadline and no internal derivation, the field is either hardcoded or set to a far-future constant. · Impact: users have no way to abort a stale transaction, which is the precondition for all delayed-execution MEV; without it every pending swap is an option handed to the block builder. · FP guard: safe if the function is only callable atomically inside a user's own transaction (a keeper/callback pattern where the swap cannot be left pending) — check the call graph before flagging.

- **Hardcoded pool fee tier or route with no existence or depth check** — Trigger: `fee: 3000` (or an equivalent fixed pool selector / hardcoded path array) with no prior check that the pool exists and holds liquidity. · Test: for the specific token pairs the protocol can be configured with, resolve whether the chosen tier pool exists and what its depth is; also check whether the swap path is configurable by an admin or immutable. · Impact: the swap either reverts — in which case the token is permanently stuck if this is the only exit path — or executes through a near-empty pool at catastrophic price impact, converting the full amount into dust. · FP guard: only a false positive if every reachable token pair is proven to have the chosen tier with adequate depth; on a live protocol verify against the actual pools rather than assuming the default tier exists.

- **No fallback exit for a token that cannot be swapped** — Trigger: a single function (`sellProfits`, `harvest`, `swapAndSend`) is the only way value leaves the contract, and it hard-depends on a successful swap. · Test: enumerate every token the contract can end up holding and every function that can move each one out; look for an asset with exactly one exit route. · Impact: if that route ever fails (no pool, paused router, zero liquidity, delisted token), the value is stuck permanently with no admin recovery — an accumulating, unrecoverable balance that stranding logic then mis-accounts for. · FP guard: safe if a rescue/withdraw function exists for arbitrary tokens, or if failure is provably impossible (the pool is protocol-owned and always liquid).

- **Fixed gas stipend on a native-currency payout** — Trigger: a low-level `call{value: x, gas: N}` or a hardcoded stipend for sending ETH to an arbitrary recipient, where `N` is small (a few thousand gas). · Test: send to a contract recipient with a payable fallback that consumes more than `N` (or a proxy that adds overhead) and check whether the transfer silently fails. · Impact: the recipient's funds are permanently unclaimable — the payout does not revert, so the accounting advances while the value stays stranded in the contract; multisig and proxy recipients are the common victims. · FP guard: safe if the recipient is always an EOA or a known low-cost contract, or if the payout is fully pull-based (the user withdraws rather than being pushed to) — the pull pattern makes the whole class moot.

- **Unchecked return value of `transfer`/`transferFrom`** — Trigger: `IERC20(t).transfer(a, b)` or `.transferFrom(...)` on a statement boundary, with no `require`, no `safeTransfer`, and no post-transfer balance assertion. · Test: enumerate every token-transfer call site and check whether the boolean is consumed; for each one decide what happens if a non-reverting, `false`-returning token is used. · Impact: tokens that signal failure by returning `false` rather than reverting cause the operation to succeed in accounting while no value moves — the protocol credits a deposit or pays out a withdrawal that never happened, and the gap is directly extractable. · FP guard: safe if the token set is closed and every member reverts on failure (verify per token, not per interface), or if a balance delta is asserted around the call — a `require` on the return value is sufficient only for tokens that do return one.

- **Non-standard ERC20 assumptions across the token boundary** — Trigger: code that assumes one of the three incompatible ERC20 behaviours: returns `true`/`false` (USDT-style tokens return *nothing*), reverts on failure (some tokens return `false` instead), or has no return data at all cast into a boolean. · Test: for each integration, classify the concrete token on all three axes; then check whether a `require(IERC20(t).transfer(...))` (which reverts on a no-return token) or an unchecked call (which ignores a `false`) is used. · Impact: the entire function reverts for a well-behaved-looking major token, or accounting advances on a silent failure — one of the two failure modes is a hard denial of service on the protocol's core flows, the other is a fund loss, and which one applies depends on the token. · FP guard: safe if every token is `SafeERC20`-wrapped *and* the token set is allowlisted and reviewed for return-data behaviour — note that `safeTransfer` does not fix a token that returns `false` without reverting on transfers that are not actually honoured by its own logic.

- **Single-step ownership transfer** — Trigger: `function transferOwnership(address newOwner) public onlyOwner { _owner = newOwner; }` with no separate acceptance step. · Test: read the ownable implementation; the presence of `acceptOwnership`/`_pendingOwner` confirms a two-step pattern, its absence with a direct assignment confirms single-step. · Impact: one typo permanently hands every `onlyOwner` capability — fee setters, minting, fund receiver, pause — to an address nobody controls; the contract becomes unadministrable and funds that require a privileged call to move are frozen forever. · FP guard: safe if ownership is renounced to a governance contract that can recover, or if the privileged surface is truly non-critical (no fund movement, no minting) — check what `onlyOwner` actually gates before assigning severity.

- **No zero-address validation on a new owner or payout recipient** — Trigger: `_owner = newOwner;` or `registry[id]` resolved into a `safeTransfer` recipient with no `require(x != address(0))`. · Test: for every address-valued setter and every payout recipient, check for an explicit zero check; then confirm whether a zero-recipient transfer reverts for the specific token (many do not). · Impact: value sent to `address(0)` is burnt irrecoverably, and a zero owner locks out all privileged functions — both are one-transaction, total losses caused by configuration rather than attack, which makes them trivially reachable but also easy to miss. · FP guard: `safeTransfer` does not protect against a zero recipient, which is the common false-negative here; conversely a zero check that exists at the setter but not at the use site is still a finding if the storage slot can be initialised to zero.

- **Single key with unilateral control over a funds-critical setter** — Trigger: `setFee`, `setFeeReceiver`, `mint`, or a fund-withdrawal function guarded by `onlyOwner` with one EOA as owner and no timelock. · Test: list every `onlyOwner` function, classify each by whether it can move value or change a fee that moves value, then check who the owner is and whether a delay or multisig exists. · Impact: one compromised key can mint arbitrarily, redirect all fees, or drain — the loss is bounded only by the TVL; this is a centralisation risk rather than a code defect, so it belongs in the report as a trust assumption. · FP guard: not a "bug" and often out of scope for a contest — only report where the design explicitly promises trustlessness (a decentralised claim) or where the privileged function can harm third parties who have already committed funds (retroactive fee changes on live positions).

- **Same balance decremented twice in one code path** — Trigger: a helper applies a delta (`_updatePoolBalance(id, current - debt)`) and then the same field is written again inline (`poolBalance -= debt`) in the same function. · Test: for every balance-like state variable, list all writes in the function and hand-sum the deltas; a unit test caching the value before and after is the cheapest confirmation. · Impact: the pool/ledger is debited twice, permanently understating liquidity — later withdrawals fail against a phantom balance and the shortfall lands on the last users to exit. · FP guard: safe if the two writes target different ids, or if the inline write is over a `memory` local that never persists — verify the storage pointer before flagging, since a `memory` copy is the most common reason this is not a bug.

- **No isolation check between source and destination account** — Trigger: a move/transfer/refinance/migration function that computes a source id and accepts a destination id as a parameter but never asserts they differ. · Test: call with `destination == source` and hand-compute every balance update in both directions; look for a non-zero net delta. · Impact: self-referential moves corrupt the accounting on each call — the observed net loss (often exactly the fee) is extractable and repeatable, and the corrupted balances can make the system insolvent without any external attacker. · FP guard: safe if the same-id case is explicitly rejected, or if the two updates are provably idempotent when applied to the same account — do the arithmetic rather than assuming the guard exists.

- **Idempotency: the same state-changing call repeated with identical inputs** — Trigger: any function that advances a counter, decrements a balance, deletes a record, or flips a status, without a guard on the current state. · Test: call the function twice with identical arguments in the same block and compare the resulting state against a single call; look specifically for counters that reach zero, records deleted twice, and status flags that move past their terminal value. · Impact: repetition either double-counts a benefit (claim twice, accrue twice) or drives a shared counter to a state that unlocks something it should not — the classic form being a "facility fully repaid" transition reached by closing records that were never real. · FP guard: safe if the function's effect is a function of state (idempotent by construction), or if a status/flag is checked and moved atomically before the effect — only the *absence* of such a guard plus a counter or status transition is a finding.

- **Privileged scalar used as a multiplier with no upper bound** — Trigger: a keeper/admin parameter consumed as a ratio against a fixed denominator — `(amount * param) / PERCENT_PRECISION` — with no `require(param <= PERCENT_PRECISION)` either at the setter or at the use site. · Test: pass a value above the denominator and trace the arithmetic; check whether the result can exceed the quantity being scaled (i.e. withdraw more than exists). · Impact: one privileged call accounts for value that does not exist, wiping out a solvency buffer or releasing collateral against unpaid debt — an instant, protocol-wide break caused by a single mis-set number, reachable by any compromised or mistaken keeper. · FP guard: safe if the parameter is bounded at both the setter and the use site, or if the result is clamped to an available balance — a bound at the setter alone is insufficient if the setter is not the only writer or if the stored value predates the check.

- **Non-existent id returns a zero-valued record that satisfies the guards** — Trigger: `Record memory r = records[id];` with no existence sentinel, followed by guards of the form `if (r.amount > 0) revert` that a zero record passes. · Test: call every function that takes an id with an id that was never created, and check whether execution reaches a state-changing branch; then check what the side effects are (counter decrements, deletes, status flags). · Impact: fabricated or uninitialised ids drive real state transitions — the standard outcome is a shared counter being walked to its terminal value so a facility is reported settled with nothing settled, or a payout being released against an instrument that never existed. · FP guard: safe if ids are provably minted monotonically and validated against a created flag, or if `records[id].someField != 0` is checked before use — note that a `mapping` read never reverts, so this is entirely a discipline question and the compiler will not help.

- **Extreme values on a division by price** — Trigger: a valuation or liquidation path that divides by an oracle price — `amount * 10**decimals / price` — with no bounds check on the price. · Test: evaluate the expression at a 99% price drop, at a near-zero price, and at zero; check for overflow in the numerator, division by zero, and a result so large that a later subtraction underflows. · Impact: the position is most distressed exactly when the arithmetic breaks, so the liquidation path reverts precisely when it is needed — a distressed position becomes bad debt rather than a recovered one, and the failure is triggered by ordinary market conditions rather than an attacker. · FP guard: safe if the price is bounded below by a sane minimum and the derived amount is capped to the available collateral — check whether the oracle itself enforces bounds before flagging, since a bounded feed makes this unreachable.

- **Arithmetic inside an `unchecked` block** — Trigger: `unchecked { ... }` wrapping a subtraction or addition whose operands include user-supplied or externally derived values. · Test: list every `unchecked` block and classify each operation: provably-safe counter increments are fine; anything subtracting a user-controlled amount from a stored balance is not. · Impact: an underflow wraps to ~2^256 instead of reverting, so a repayment exceeding the debt turns a healthy position into an astronomically-indebted one — instant, forced liquidatability for one transaction of capital, or a share balance that mints unlimited value. · FP guard: safe when the operands are proven ordered by a check earlier in the same function (`require(positionLiquidity >= params.liquidity)` immediately before the subtraction is the correct pattern) — the guard's presence within the same function scope is what clears it, not the comment justifying it.

- **Bound-exceeding input not clamped before the state update** — Trigger: `repay`/`withdraw`/`deposit` accepting an amount larger than the outstanding balance or the deposited principal, with no `require(amount <= owed)` and no internal clamp. · Test: call the bound function with 2× the outstanding amount and inspect the resulting stored debt; a clamp, a revert, or a wrapped value are the three possible outcomes and only the first two are acceptable. · Impact: at best the excess is silently absorbed (user loses funds to the protocol), at worst it wraps and forces liquidation; either way a single mis-sized transaction produces a permanent state inconsistency. · FP guard: safe if the amount is clamped inline (`amount = min(amount, owed)`), which is equivalent to a revert for the user's exposure but must be *read* rather than assumed — and check whether the return value reports the clamped amount so callers can reconcile.

- **Iteration order assumed over a container that does not guarantee it** — Trigger: `EnumerableSet.at(i)` / map iteration / `.keys()[i]` indexed in a loop, where the code's correctness depends on element order being stable across the loop or across transactions. · Test: identify the container implementation and whether it documents an ordering guarantee; then write a case with enough elements that an insertion or removal provably reorders. · Impact: the code reads a different element than it intends — the failure mode is either a wrong-value computation that silently corrupts state, or an index-out-of-bounds revert that makes the whole operation impossible for any account holding more than the reorder threshold. · FP guard: safe if the code only ever needs *some* element rather than a specific one, or if the container is an array with explicit ordering semantics — the bug requires that correctness depend on order, not merely that a set is used.

- **Removal reorders the collection during iteration** — Trigger: a loop over a set/array that calls `remove`/`erase` inside the body, where removal uses swap-and-pop or any scheme that moves the last element into the removed slot. · Test: construct the multi-element case (three or more, so a swap is not a simple truncation) and check whether the loop re-processes or skips elements, or indexes past the new length. · Impact: elements are skipped or double-processed — the dangerous direction is skipping, because it means some accounts' positions are never processed while the operation reports success, producing permanently un-liquidatable or un-settleable state. · FP guard: safe if the ids are first cached into a memory array, if the loop iterates downwards from the initial length, or if removal happens strictly after the loop — verify the container's actual removal semantics rather than assuming `remove` is stable.

- **Configuration change applied retroactively to live positions** — Trigger: a setter for a fee, oracle, collateral factor, or allowlist that writes one global value which live positions read at use time rather than at open time. · Test: open a position, change the parameter, and check whether the *existing* position's liability or valuation changes; then check whether the position was opened under an expectation the setter can now break. · Impact: the counterparty who has already committed funds bears a unilateral term change — the extreme form being a fee or oracle swap that makes an existing healthy position immediately liquidatable. · FP guard: safe if the parameter is snapshotted into the position at open, if changes are timelocked longer than the longest position term, or if changes are constrained to be no-worse-for-existing-positions (and the constraint genuinely covers every field).

- **Fee computed on a pre-clamp value rather than the value actually transferred** — Trigger: an amount is capped (`if (x > cap) x = cap;`) and then a fee/surcharge/penalty is computed from the uncapped expression instead of from `x`. · Test: find every clamp and check which variable each downstream computation reads; a fee on the uncapped value exceeds the value available and will underflow on subtraction. · Impact: the payout underflows and reverts, or the fee silently exceeds the transfer — in the liquidation case this manifests as the protocol being unable to liquidate a position precisely when it is most distressed, converting distress into bad debt. · FP guard: safe if the fee is derived from the clamped value or from `min(raw, capped)`; verify the decimal scaling before claiming an overflow, since a units mismatch can look like this bug and is not.

- **Comment or documentation asserts a permission the code does not enforce** — Trigger: a `/// onlyOwner`-style comment, a NatSpec claim, or an interface docstring stating an access restriction that no modifier or `msg.sender` assertion implements. · Test: for each commented permission claim, check the function body for a modifier or an explicit assertion; a comment with neither is unenforced. · Impact: reviewers and integrators rely on the stated model and build on it — an unenforced `owner only` on a funds- or role-moving function is a direct unauthorised-action path, and the mismatch is invisible to anyone reading docs rather than bytecode. · FP guard: safe if the constraint is enforced one level up in the call graph (an internal function whose only callers are guarded) — trace all callers before flagging, but if any caller is `external` the claim is false.

- **Activation or launch gate keyed on a rate rather than accumulated totals** — Trigger: a one-way transition (`enableLaunch`, `startTrading`, `unpause`) gated on `unitPrice >= thresholdPrice` or a per-unit quantity, where the operational requirement is on the aggregate (total raised, tokens sold, ETH collected). · Test: solve for the number of units at which the rate condition first holds, and separately for the number of units needed to satisfy the real requirement; compare the two and quantify the gap. · Impact: the gate opens before the protocol has the resources the gate exists to guarantee — the launch proceeds underfunded, the pool is seeded short, and the shortfall is socialised to the participants who bought in believing the condition was a solvency check. · FP guard: safe if the rate is a provable sufficient statistic for the aggregate (usually only when the unit count is fixed), or if a second check covers the aggregate — look for the second check before flagging, since a belt-and-braces gate is common and this is then informational.

- **Magic-number mint instead of a computed shortfall** — Trigger: a mint/burn that writes a constant or a value derived from a config field rather than `target - totalSupply()`. · Test: run the arithmetic for two different transaction histories that should both end at the same target supply, and check whether both do; also test the boundary cases just below and exactly at the threshold. · Impact: the terminal supply is off by a variable amount that depends on the path taken, so the fixed invariant the protocol promises (an exact supply, an exact pool ratio) is violated — every downstream calculation that assumes that number inherits the error. · FP guard: safe if the constant is provably the correct remainder for every reachable path (rare), or if a reconciliation assert closes the gap — a mint that happens to be right in the tested scenario is not evidence.

- **Post-mint/post-burn reconciliation invariant not asserted** — Trigger: a state transition that must leave a derived total at an exact value, with no `require(total == target)` at the end. · Test: after the transition, recompute the invariant from the new state and assert it; then look for the paths that can leave it unmet. · Impact: the invariant drifts silently and is only discovered when a downstream consumer (a pool, a ratio-based fee, a redemption rate) mis-prices against it — the failure surfaces far from its cause and looks like a pricing bug rather than an accounting one. · FP guard: not every sum needs an assert — only assert where a later calculation *depends* on exactness; where the value is cosmetic or advisory this is noise, and adding an assert that can never trip is worse than no assert.

- **Maximum-amount pull before an external call with no refund of the unused balance** — Trigger: `safeTransferFrom(user, address(this), maxAmountsIn[i])` followed by a pool/router call that consumes only part of it, with no `balanceOf` sweep afterwards. · Test: provide a `max` larger than the pool absorbs, complete the operation, and check the contract's residual balance against the user's expectation. · Impact: the unused portion is stranded in the contract — not stolen, but permanently inaccessible to the user who authorised only the *maximum*; on a shared router the residue is also claimable by a later caller depending on the withdrawal logic. · FP guard: safe if the contract sweeps the residual back to `msg.sender` at the end, or if the external call consumes exactly the passed amount by construction — read the sweep, don't infer it from the allowance pattern.

- **Discrete threshold inside a continuous rate formula** — Trigger: a rate/price computed by one formula below a boundary and a different formula (often a constant) at or above it — `if (collateralLevel <= COLLATERAL_THRESHOLD) rate = f(...); else rate = FIXED;`. · Test: evaluate both branches at the boundary from both sides and compute the jump; then compute the value transfer between holders that the jump implies at realistic supplies. · Impact: a tiny movement across the threshold moves value between two holder cohorts in a single step — one side loses the difference and, because the boundary is reachable and the move can be induced with a small deposit, the transfer is extractable by whoever crosses it deliberately. · FP guard: safe if the two branches are continuous at the boundary (compare the limits, don't assume), or if the threshold cannot be crossed by a single small transaction given the pool's size.

- **Fee or interest bypassed by acting before the scheduled fee event** — Trigger: fees are charged only during or after a periodic event (an auction, a distribution, a harvest), while the exit/redeem path does not deduct the accrued share at the moment of exit. · Test: exit immediately before the event, compare the realised rate against the fee-inclusive rate, and confirm the fee was never deducted from this position. · Impact: the exiting holder's share of the fee is redistributed to those who stay — a repeatable, gas-cheap extraction that grows with the number of holders who learn it, and it degrades the yield of the honest cohort rather than the protocol's own balance. · FP guard: safe if the fee is accrued continuously (per block or per share) rather than at discrete events, or if exiting before the event forfeits an equivalent amount — check what the exiter gives up before flagging.

- **Schedule advanced by assignment to `block.timestamp` instead of by the interval** — Trigger: `lastDistribution = block.timestamp;` in a function guarded by `require(lastDistribution + period < block.timestamp)`. · Test: introduce a small execution delay, then check whether the next scheduled event moves by that delay; repeat and confirm the drift accumulates. · Impact: every late execution pushes the entire schedule permanently later, so yield-bearing events fire progressively less often than designed — the loss is spread across all participants and compounds monotonically over the protocol's life. · FP guard: safe if the schedule is anchored to a fixed epoch (`last = last + period`, or a modulo of an origin), or if the drift is bounded by a re-anchoring rule — an explicit "catch up" branch clears it.

- **Unvalidated user input inflating an aggregate that gates the whole operation** — Trigger: `totalSellReserveAmount += buyReserveAmount;` where `buyReserveAmount` is caller-supplied and unbounded, and a later condition compares that aggregate against a pool balance. · Test: supply a single oversized value, check whether the aggregate crosses the gating condition, and then check whether the caller loses anything (is there a refund/reversal path?). · Impact: one cheap transaction trips a global failure condition and blocks the operation for everyone — a denial of service on the protocol's core flow, and if the caller can recover their input the attack is nearly free. · FP guard: safe if the input is bounded by an allowance/balance that must actually be transferred, or if the gating comparison is against a separately tracked quantity — verify whether the inflating value is ever *moved*, since a purely accounting inflation is the whole bug.

- **Two-step proportional reduction with double truncation** — Trigger: `proportion = (amountToRemove * 1e18) / total; reduction = (bidAmount * proportion) / 1e18;` — two successive truncating divisions to express one ratio. · Test: run the reduction with values chosen so both divisions truncate, then recompute the implied price ratio before and after; a ratio change means value moved between participants. · Impact: the truncated remainder alters the effective price each participant pays or receives, so one side is systematically under- or over-charged — the drift is small per operation but accumulates and is exploitable by choosing values that maximise the truncation. · FP guard: safe if the ratio is preserved by construction (compute the reduction as a single `mulDiv`), or if a post-condition asserts the aggregate did not move in the wrong direction — an explicit "invariant did not degrade" check is the correct mitigation and its absence is the finding.

- **Allowance increase against a token that already reports infinite allowance** — Trigger: `token.safeIncreaseAllowance(spender, amount)` where the token is a pool/LP token whose `allowance` implementation returns `type(uint256).max` for the canonical spender. · Test: read the token's `allowance` semantics for that spender, then evaluate `oldAllowance + amount` — if the old value is `type(uint256).max`, the addition overflows and the function reverts unconditionally. · Impact: the exit/redeem path reverts for every user of that token — a permanent, total denial of service on withdrawals, caused by defensive code added for exactly the wrong token class. · FP guard: safe if the code uses `forceApprove`/direct `approve` rather than an increase, or if the token is verified not to return an infinite allowance; the pattern is otherwise *good practice*, so check the specific token's behaviour before flagging.

## Sequence

1. **Fix the unit and precision conventions first.** Write down the decimals of every token, the scaling constants (`1e18`, `10000`, `BPS`, `WAD`), and the rounding direction each expression uses. Two-thirds of the entries above are only decidable once the units are pinned — a units error masquerades as an overflow, a truncation, or a fee bug.
2. **Tabulate every internal and external transfer.** For each: is the return value consumed, is the token allowlisted, does the token return data, and what is the recipient (can it be `address(0)`, the contract itself, or a contract with a costly fallback)? This one table resolves the whole ERC20-quirk, zero-address, and gas-stipend group.
3. **List every state variable, then every write to it.** For each variable, collect all writes across the codebase and look for: a field written twice in one function, a balance written without a matching counter-write, a setter that feeds a value read by live positions, and a clamps-vs-fee mismatch. This is the accounting pass, and it is where the highest-value findings usually are.
4. **Walk every guard from both sides.** For each `require`/`if…revert`: what is the operand's admissible range, is the comparison strict or inclusive, and what value reaches the boundary? Then re-evaluate every multiplicative guard at zero and at the maximum. Covers the boundary, zero-bypass, and unvalidated-range entries.
5. **Check every loop for mutation and placement.** Inside a loop body: does it remove from the collection it iterates, rely on element order, or evaluate an invariant using accumulators that are still zero on the first pass? Cache-to-memory and move-the-check-after-the-loop are the two fixes; find the loops that need them.
6. **Trace every schedule and every threshold.** For each time- or level-based branch: is the state advanced by a fixed interval or reset to `block.timestamp`; is the branch continuous at its boundary; and can a single small transaction cross it? Then check who can act just before the event to escape a fee.
7. **Audit the privileged surface as a set, not per function.** Enumerate `onlyOwner`/role-gated functions, bound every parameter they accept, and check the setter *and* the use site. Then check the ownership transfer pattern and whether any privileged function can harm funds already committed.
8. **Run the idempotency sweep last.** For every counter, status flag, and delete, call the function twice with identical inputs and diff the state. This is cheap, mechanical, and catches the terminal-state bugs that a read-through misses.
9. **For each finding that survives, write the falsifier before writing it up** — a number, an assertion, or a one-line test. If none can be written, it is a heuristic candidate, not a finding.
