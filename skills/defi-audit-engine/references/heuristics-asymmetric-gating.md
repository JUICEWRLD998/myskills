**Scope:** asymmetric gating — the class our own S1-mirror shape targets: an action, flag, or guard that applies to one side of a mirror pair and not the other, so one party can act while the counterparty cannot, or a state change unblocks one side only. Sub-shapes: sibling-function asymmetry (an allowlist or pause flag on `repay` but not `liquidate`), pause/stale-price state blocking the user's escape hatch but not the liquidator's or keeper's, flags set on one path with no inverse reset, and per-function-permission tabulation as the detector. Ordered by expected yield. Derived from `Lending/State-Pause/` (all 5 directories), `Lending/Liquidation-issues/{Repayment-Liquidation,prevent-Liquidation,Impossible-Liquidations,avoid-liquidation,disable-market}/`, `Lending/State-Pause/collateral-pause/Liquidation-orders/`, `Lending/State-Pause/Freez-deposit/`, `Lending/State-Pause/prevent-users/`, `BEEDLE/ownershiptransfer/`, `PLAZA-FINACE/HIGHS/H-6/`, and the asymmetry triggers in `General-Checklis.md`.

- **Sibling-function gating asymmetry on a mirror pair** — Trigger: two functions that perform the inverse or component operations on the same state (repay and liquidate, deposit and withdraw, open and close, mint and burn, grant and revoke) where one carries a modifier or inline gate and the other does not. · Test: build the per-function-permission table (rows = entrypoints, columns = every protocol-wide modifier/flag/allowlist) and read the rows as bit-strings; a cell populated in one row and empty in its mirror row is the finding. · Impact: the ungated direction is the one an attacker or a distressed counterparty wants, so the asymmetry converts a protective mechanism into a one-way door — the source material's canonical case is a token allowlist whose check is on `repay` but absent from `liquidate`, letting positions be force-closed with an asset the owner is forbidden from using to defend. · FP guard: safe where the two functions legitimately have different threat models (a gate that exists to protect the *protocol's* entry points need not apply to an exit), so read the gate's intent and the revert message before flagging — the finding is that one side can act when the other cannot, not that the modifier lists differ.

- **Pause flag applied to repayment but not liquidation** — Trigger: `repay()` opening with `if (!isRepayAllowed()) revert;` while `liquidate()` reaches the same internal repayment routine with no equivalent check, or vice versa. · Test: flip the flag off and confirm which side still executes; then flip it on and check whether anything delays or bounds the liquidation side. · Impact: the protocol can unilaterally stop every borrower from reducing debt while liquidators keep operating — positions that drifted during the pause are force-closed the moment it lifts, with the borrower locked out of the only two actions (repay, add collateral) that could have saved them. · FP guard: safe if the flag is scoped to *new* borrowing only, or if liquidation carries an equivalent-or-stronger gate — check whether a grace period exists before concluding the asymmetry is exploitable rather than merely asymmetric.

- **Guard/context check that requires an external protocol call on one side only** — Trigger: a security check implemented by exercising an external contract — `ICurve2TokenPool(pool).remove_liquidity(0, minAmounts)` used as a reentrancy/context probe — placed on the liquidation path but not on the user paths, or the reverse. · Test: enumerate the concrete implementations the protocol can be pointed at, run the probe call against each with zero/edge arguments, and check whether any revert; then check which entrypoints are gated by the probe. · Impact: liquidation is impossible for the affected pools (the probe reverts for that implementation) while user actions are unaffected — or, read the other way, the asymmetry means one class of user can be locked out by a check the other class never triggers. Either direction produces positions that cannot be resolved. · FP guard: safe if only one implementation is ever registered and it is proven to handle zero arguments — verify against the registry's actual contents, not the interface.

- **Pause blocks the user's remedy but not the liquidation** — Trigger: the pause/frozen flag is read in `close`, `repay`, `depositCollateral`, and `increaseCollateral` but the liquidation entrypoint carries only `notPaused` (or nothing), and there is no post-resume delay. · Test: pause, move the price against a position, unpause, and determine whether a liquidation can be included before the borrower's first possible defence transaction — compare ordering within the same block, not just eligibility. · Impact: the borrower absorbs market moves they were forbidden from reacting to, and liquidation bots capture the entire difference; this is repeatable at every pause, is visible in the transaction ordering, and makes the protocol look complicit in the extraction. · FP guard: safe if a grace period of at least the pause length (capped, and enforced on-chain) delays liquidations after resume — verify the delay exists in code with a timestamp comparison, not in the comments.

- **Pause blocks both directions, trapping users and creating bad debt** — Trigger: a single flag (`collateralValid[addr] = false`) is read by both `closeLoan` and `callLiquidation`, so pausing a collateral type short-circuits every exit path. · Test: pause a collateral type while loans against it are open, then attempt (a) repay-and-close, (b) liquidate a now-underwater position; if both revert, the collateral and the debt are both frozen. · Impact: borrowers cannot recover their own collateral and the protocol accumulates loans that can never be resolved either way — a governance-triggered, permanent bad-debt hole, and the mirror of the more common asymmetry (here the *user* is blocked alongside the liquidator, so neither side can act). · FP guard: safe if the pause only blocks new deposits/loans and explicitly exempts close and liquidation — the correct scope is almost always "stop new exposure, allow resolution", so flag any pause that also stops resolution.

- **Internal-accounting-only path bypasses a freeze that blocks the counterparty's actions** — Trigger: the liquidation branch only adjusts internal numbers (`values.pnlAmountForPool = collateralAmount - fundingFee`) while close and add-collateral perform `safeTransferFrom` — so a paused/blocked collateral token stops the user but not the system. · Test: freeze the collateral token, then classify {close, addCollateral, liquidate} by which revert; if the user-facing paths revert and the liquidation path does not, the asymmetry is live. · Impact: forced liquidation of positions whose owner had no ability to intervene, plus a second-order risk — an accounting-only "liquidation" that never moves tokens leaves the pool's books claiming value it never received, so the loss can be double-counted. · FP guard: only a false positive if the collateral is provably held somewhere the freeze does not reach, or if a separate unpaused exit exists for users — check the token's actual pause semantics per collateral, not the interface.

- **Live-price / freshness gate demanded on one side of a mirror pair only** — Trigger: a shared `_checkIfCollateralIsActive` / stale-price / circuit-breaker check applied unconditionally at the top of one function while a sibling that needs the same valuation does not apply it, or the reverse (valuation runs on a stale price while execution is gated). · Test: trip the stale flag, then run the same logical operation through both sides and compare; also check whether the valuation used by the ungated side reads a cached price with no freshness bound. · Impact: the gated side is a denial of service whenever the feed stales (a market-wide condition), and the ungated side computes against a stale price — either direction transfers value, and the two failure modes can coexist in the same codebase. · FP guard: safe if the check is conditional on remaining exposure (`if (outstanding > threshold)`) rather than unconditional, which is the correct fix — diff the branch, not the call site.

- **Risk-reducing action gated by a check that only matters for risk-increasing actions** — Trigger: `increaseCollateralAmount` recomputing the liquidation margin (`require(colInUSD >= borrowMargin)`) and reverting on stale prices, when adding collateral strictly improves the position. · Test: with a stale or depressed price, attempt to add collateral to an underwater position; also check whether a fully-repaid loan can be closed while the feed is stale. · Impact: the single action that could rescue a position is the one most likely to be blocked, converting recoverable positions into liquidations — a loss to both the borrower and the protocol, caused purely by gating placement. · FP guard: safe if the check is a no-op for positive additions, or is skipped entirely on the add path — this is a one-line fix, so the finding is the gate's *location*, not its existence.

- **Flag set on one path with no inverse reset** — Trigger: `pause()` writes the flag, `unpause()` is missing, or `unpause()` clears one of two flags, or the pause is per-asset while the unpause is global (or vice versa). · Test: for every state flag, enumerate all writers and check that each pole of the flag has a reachable setter and that the setters touch the same set of variables. · Impact: the flag can be entered but not left (or left incompletely), so the gated behaviour persists beyond the condition that justified it — a one-way switch on the protocol's core flows, and in the per-asset case one asset's flag can strand every asset. · FP guard: safe if the flag is deliberately monotonic (a permanent shutdown, documented as such) or if the asymmetry is compensated elsewhere — a global unpause that resets all per-asset flags is not a bug.

- **No grace period or delay after the flag flips back** — Trigger: the unblocking path (`unpause`, `enableMarket`, `allowRepayments`) writes the flag and returns, with no timestamp recorded and no consumer of one. · Test: grep the unblock path for a stored timestamp and check whether any liquidation function compares against it. · Impact: the state change immediately opens the action the flag was blocking, so every position that drifted while blocked is resolved in the same block as the resume — the bots' advantage is total and the borrowers' reaction time is zero, which is the difference between a paused protocol and a trap. · FP guard: safe if liquidations are separately delayed, if the pause was short relative to the price move, or if borrowers had an out-of-band exit — check whether an alternative exit exists before assigning severity, since this is a liveness/selection issue rather than a pure bug.

- **Market, asset, or token disabled while positions remain open** — Trigger: `updateMarketStatus(false)` / `delistToken` / `disableMarket` with no `require(openPositions == 0)`, while the close path reverts on a disabled market and liquidation does not. · Test: open a position, disable the market or delist the asset, then attempt (a) close, (b) liquidation after a price move — confirm the asymmetry and check whether closing/reducing is exempted. · Impact: traders are locked into positions they can only lose on; the operator's switch becomes a mechanism for converting user equity into liquidation fees, and the same switch is a censorship vector against any specific account. · FP guard: safe if reducing/closing is explicitly exempted on a disabled market, or if disabling requires zero open interest or a timelock — an emergency switch that halts *new* exposure is correct design and should not be flagged.

- **Delisting scoped to new business that leaks into existing positions' exit path** — Trigger: `onlyWhitelistedToken(token)` on `repay` — a modifier whose intent is to gate new borrowing — applied to the repayment of positions created when the token was allowed. · Test: for each allowlist modifier, determine whether it gates *creation* or *operation*; then delist an asset used by an open position and check whether the owner can still repay and close. · Impact: the borrower cannot exit a position in a de-listed asset while liquidation (which lacks the modifier) still runs — a governance action converts directly into forced loss of collateral, and the asymmetry is invisible because each modifier looks correct in isolation. · FP guard: safe if de-listing is scoped to new loans with an explicit exemption for existing ones, in both the repay and the collateral path — check both paths, since exempting one and not the other reproduces the same bug.

- **Existence check standing in for authorisation, asymmetrically between grant and revoke** — Trigger: `removeFeeder(x)` / `revokeRole(x, account)` guarded only by `onlyWhenFeederExisted(x)` while the granting path carries a role check — so presence is tested but permission is not, and only on the negative side. · Test: classify each modifier body as presence-vs-permission, then build the role matrix (who can grant, who can revoke) and look for revoked-by-anyone where granted-by-admin. · Impact: any account can revoke a role that a load-bearing function depends on — in the source instance, revoking the price feeder stales the oracle, the price getter reverts, and every liquidation becomes impossible, so a borrower one step from liquidation permanently escapes into bad debt. · FP guard: safe if a second modifier on the same function carries the role check (read all modifiers, not the first), or if permissionless revocation is deliberate — even then, note the liveness risk when the role is critical.

- **Operator kill-switch on one side of the mirror, held by one role, with no bounded expiry** — Trigger: `if (liquidationsLocked) revert;`, a `liquidationAuctionMinSpacing` check, or a global "min auction spacing" settable by the same role that can also pause or move collateral. · Test: set the switch, advance time, and confirm every liquidation path (including seize-on-expiry) reverts; then check who can set it, whether it auto-expires, and whether any unset path exists. · Impact: one flag makes every distressed position unrecoverable — a single point of protocol-wide insolvency, and a cheap griefing vector if the role is not tightly held or if the spacing check can be re-triggered by a third party to keep resetting the window. · FP guard: safe if the lock is short-bounded and auto-expiring, cannot be set while positions above a risk threshold are open, or is scoped to a single market — verify the bound in code before treating this as critical.

- **One counterparty can unilaterally change terms the other cannot** — Trigger: an update function callable by one side of a bilateral position (lender, operator, borrower) that mutates parameters affecting the other side's valuation or liability, with the "no worse" guard omitting a field. · Test: for each bilateral parameter, list who can write it at each lifecycle stage; then diff the guard's require list against the struct's fields. · Impact: the party with update rights can make the other side's position liquidatable on demand — in the source instance a lender swaps in an under-reporting oracle and seizes collateral worth multiples of the loan; the general shape is "the party who benefits from the parameter change is the one allowed to make it". · FP guard: safe where changes are constrained to be strictly no-worse for the counterparty *and* the constraint demonstrably covers every field — an incomplete guard list is the finding, so enumerate the fields rather than reading the intent.

- **Cooldown, delay, or rate-limit applied to one side of a mirror pair** — Trigger: a timelock/cooldown on the user's action (withdraw, close, exit) with no equivalent on the other side's action (liquidate, seize, settle), or a rate-limit that applies to deposits but not withdrawals. · Test: for each time-based gate, find the operation it delays and then check whether the mirror operation has one; compare the delays. · Impact: the delayed side is systematically slower than the side racing it, so the party that must react loses to the party that acts — with an imbalance this large the difference is extractable rather than merely unfair, and the extraction shows up in ordering rather than in code. · FP guard: safe where the cooldown protects the counterparty (a withdrawal delay that prevents a bank run is the *intended* asymmetry) — check which side the delay protects and whether it is documented as such.

- **Fee, interest, or accrual event charged on one path but bypassable on a mirror path** — Trigger: fees are moved only during a periodic event (auction, distribution, harvest) while the redeem/exit path does not deduct the accrued share at exit. · Test: exit immediately before the event, compare the realised rate against the fee-inclusive rate, and confirm the fee was never taken from this position — then check whether the exiter forfeits anything equivalent in exchange. · Impact: the exiting holder's fee share is redistributed to those who stay, so the extraction degrades the honest cohort rather than the protocol's own balance; it grows with the number of holders who learn it, and the window is predictable from on-chain state. · FP guard: safe if the fee accrues continuously per share rather than at discrete events, or if early exit forfeits an equivalent amount — a cliff in either direction converts the bypass into a no-op, so check what the exiter gives up.

- **Emergency halt that stops inflows but not outflows, or the reverse, in a value-transferring way** — Trigger: a pause that blocks deposits/borrows but leaves withdrawals/repayments open (or the mirror), with no economic rationale for the direction. · Test: for the halt, classify each gated entrypoint as inflow or outflow and check the economic consequence of the surviving direction at the current state — a borrow-only halt, for instance, prevents positions from being opened but lets an attacker repay-and-close at a stale price. · Impact: whichever direction survives becomes an option granted to whoever notices — the classic form is a withdrawal halt that lets the operator exit while users cannot, or a deposit freeze that locks users into a position they would exit. · FP guard: safe where the surviving direction is the one that reduces protocol risk (allow repayments and liquidations during an emergency, block new exposure) — that is the correct shape and should not be flagged; the finding is a halt that protects one party at the other's expense.

- **Price-freshness gate applied asymmetrically between valuation and execution** — Trigger: the health/valuation function reads a cached or unbounded-age price while the execution path enforces a freshness bound (or the opposite), so the two sides of a decision are computed on different price vintages within the same transaction. · Test: write down, for a single liquidation call, every price read on the path — the health check's, the seizure calculation's, the fee's — and compare their sources, timestamps, and staleness bounds. · Impact: the decision and its execution use different numbers, so a position can be judged liquidatable on a stale price and seized at a current one (or the reverse, producing a liquidation that should not have happened). The discrepancy is a direct, quantifiable value transfer between the position's owner and the liquidator. · FP guard: safe if all price reads on a decision path resolve to the same source and the same bound — a single cached read at the top of the function is correct design; multiple independent reads are the finding.

## Sequence

1. **Build the gate matrix before reading any logic.** Rows: every `external`/`public` function. Columns: every protocol-wide flag, modifier, allowlist, role, and time-gate. Fill it from the code, then read the *columns* — a column with a single populated cell, or a mirror pair of rows whose cells differ, is the finding. This one artifact produces most of this file's entries and is faster than reading the functions one at a time.
2. **Pair the entrypoints explicitly.** Write down the mirror pairs (repay↔liquidate, deposit↔withdraw, open↔close, grant↔revoke, pause↔unpause, enable↔disable, mint↔burn, add↔remove) and for each pair list the gates on both sides. Asymmetry is invisible for a single function read in isolation, which is why this class survives review.
3. **Enumerate the flags and force a state table.** For each flag: what sets it, what clears it, what reads it, and what happens if it is never cleared. Then check that both poles are reachable and that the clearing path touches the same variable set as the setting path.
4. **For every state-changing path, ask who is *unable* to act.** This is the S1-mirror question in its general form — for each blocked action, identify the counterparty action that is not blocked, and check whether the asymmetry transfers value or only delays it.
5. **Trace every risk-reducing action and confirm it has no unnecessary gate.** Adding collateral, repaying, and closing a fully-repaid loan should never be blocked by a check that exists to gate risk-increasing actions or by a stale-price condition. This pass is short and finds real findings cheaply.
6. **Classify every modifier as presence-check or permission-check, then list callers.** A permission-shaped name with a presence-shaped body, on a function any account can reach, is the highest-severity shape in this file because its impact is direct.
7. **Check the resume path for a grace period.** For each flag that unblocks an action, look for a stored timestamp on the unblocking path and a comparison against it on the action path. Absence of both, plus positions that could have drifted while blocked, is the finding.
8. **Do the ordering analysis on the resume case.** Pause, move the price, unpause, and determine whether a liquidator's transaction can be ordered before the borrower's defence — a same-block ordering advantage is the difference between a liveness issue and an exploitable one.
9. **For each finding that survives, write the falsifier before writing it up** — a call sequence, a block ordering, or a value delta. If none can be written, it is a heuristic candidate, not a finding.
