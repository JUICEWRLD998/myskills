**Scope:** Uniswap-V3-fork / concentrated-liquidity / pool-integration codebases — price adapters and oracles built on `slot0`/`observe`, LP positions used as collateral, routers and pool-selectors, liquidity provisioning, and pool-token exit paths. *Source note: this is the thinnest bucket in the library — 2 findings in `EXPLOITS-UniswapV3/` plus scattered pool material. The entries below are all supported by source, but this file is **not** a complete concentrated-liquidity checklist: it has no coverage of tick-crossing, position-manager ownership/NFT semantics, flash-loan-callback trust (`uniswapV3FlashCallback`), protocol-fee collection, or MEV-protection routers such as `SwapRouter02`/Universal Router command decoding. - **Price returned in PriceX96 where a decimal-normalised price is expected** — Trigger: an oracle adapter computing `FullMath.mulDiv(sqrtPriceX96, sqrtPriceX96, FixedPoint96.Q96)` and returning it directly from `latestRoundData()`/`getPrice()`, with no `10**(18 + decimals1 - decimals0)` conversion. · Test: call the adapter for a known pair (e.g. USDC/WETH where the true price is ~3,245 USDC per WETH) and compare the magnitude and exponent of the returned value against the 18-decimal value the consumers assume. · Impact: every asset valuation served by the adapter is off by a factor of ~10^19 — collateral is priced at a fraction of its worth, so any position is instantly liquidatable, and the error direction also breaks the borrow-side cap. Total, universal mis-pricing of the asset. · FP guard: safe if the adapter is documented and consumed as a PriceX96-format feed end-to-end, or if the conversion happens in the consumer — trace who calls it and what units they expect before flagging, since an unconverted feed is only a bug relative to its consumers.

- **TWAP read from `observe()` with no minimum observation window** — Trigger: `ICLPool(pool).observe(secondsAgos)` with `secondsAgos[0] = twapInterval` where `twapInterval` is small or settable, and no check that `twapInterval` is within the pool's actual observation cardinality. · Test: read the pool's `observations`/`observationCardinality` and confirm whether the requested window is actually populated; then check the tick arithmetic `(tickCumulatives[1] - tickCumulatives[0]) / int56(uint56(twapInterval))` for the sign and truncation behaviour at small intervals. · Impact: a short window is a manipulable window — the attacker moves the spot price across a few blocks to drag the TWAP, borrows against the inflated collateral value, and leaves the position bankrupt; if the window exceeds the stored observations the call instead reverts, which is a denial of service on every price-consuming action. · FP guard: safe if the window is a hardcoded constant long enough to resist a multi-block push and the cardinality is verified at configuration time — quantify the push cost against the profit before assigning severity.

- **Token order not enforced in the pool key or adapter** — Trigger: a V3 pool key is constructed from two tokens, but the adapter does not record or assert which of the two it is pricing; without an explicit sort the key resolves to the wrong pool, and `slot0`/`observe` are then read against the inverted pair. · Test: call the price path with the pair in both orders and check whether the two results are inverses of one another or whether one order silently returns a price for the wrong side. · Impact: the returned price is either wildly wrong (an inverted ratio) or correct only by coincidence for the specific tokens tested — the failure surfaces on the first pair with a large decimal asymmetry, and mis-pricing is immediately liquidatable. · FP guard: safe if the code sorts the tokens canonically and maps its own orientation onto the sorted key, or if the pool is looked up by a factory call that guarantees the order — check the construction site, not just the usage.

- **Pool mapping populated in both orders without deciding which token is being priced** — Trigger: `getPool[tokenA][tokenB] = pool; getPool[tokenB][tokenA] = pool;` with no accompanying record of the orientation, so any consumer reading `getPool[x][y]` cannot tell whether the price is quoted in `x` or `y`. · Test: for a pair with asymmetric decimals, resolve both entries and check whether the adapter's decimals assumption is consistent with the actual quote direction. · Impact: the decimal context of the price is undefined, so the adapter applies the wrong scale — the mis-pricing is silent (the magnitude looks plausible) and shows up only as systematic under- or over-valuation, which is directly extractable by borrowing. · FP guard: safe if the orientation is stored alongside the pool (a struct with `base`/`quote`) or the price is always normalised to a canonical direction on read.

- **Decimals taken from the wrong token of the pair** — Trigger: `decimals = IERC20(_token).safeDecimals();` where `_token` is the asset being priced, while the pool's price is actually quoted in the liquidity/counterparty token's decimals (e.g. 18-decimal bond token vs 6-decimal USDC). · Test: for each configured pair, compare the token whose decimals are used against the token the pool quote is denominated in, and recompute the price by hand at full precision. · Impact: the price is off by `10^(d1 − d0)` (a factor of 10^12 for an 18/6 pair) — the mis-pricing direction determines whether collateral is undervalued (instant liquidations, borrower equity stolen) or overvalued (unbacked borrowing, protocol insolvency). · FP guard: safe if decimals are derived from the pool's own `token0()`/`token1()` and applied to the matching side of the quote — flag only after establishing the quote direction, since "uses token decimals" is not itself wrong.

- **LP / pool position accepted as collateral with zero liquidity** — Trigger: the collateral-deposit path can record a V3 position NFT whose `liquidity` is 0, with no `require(liquidity > 0)`, while the liquidation path unwraps it through `decreaseLiquidity` (which enforces `params.liquidity > 0`). · Test: deposit a position NFT with `liquidity == 0`, drive the account under-collateralised, and attempt liquidation; then trace `_unwrapPosition → removeLiquidity → decreaseLiquidity` for the first revert. · Impact: the borrower engineers a worthless-but-un-liquidatable position and walks away with the borrowed funds — a deliberate, repeatable bad-debt factory; because the position is free, the attacker's cost is gas only. · FP guard: safe if the deposit path rejects zero/negative liquidity, or if the liquidation path can seize the position *without* unwrapping it (a fallback that transfers the NFT).

- **`decreaseLiquidity` / `burn` preconditions unchecked on the deposit side** — Trigger: the deposit path records `position.liquidity` and later calls `decreaseLiquidity` with an amount derived from it, while `require(positionLiquidity >= params.liquidity)` is the only protection against over-withdrawal and the position may have been mutated (collected, decreased, transferred) between deposit and liquidation. · Test: for each position, re-read `pool.positions(positionKey)` at liquidation time and compare the stored `liquidity` against what the protocol recorded at deposit; test the case where the position was previously decreased or collected outside the protocol. · Impact: the removal either reverts (liquidation impossible → bad debt) or attempts to remove more than exists — the position may be owned by a third party, so the protocol's collateral claim is unenforceable and the debt is unbacked. · FP guard: safe if the protocol escrows the NFT (so it cannot be mutated externally) and re-derives liquidity from the pool on every use rather than trusting a cached value.

- **`amount0Min` / `amount1Min` left at zero on decrease or collect** — Trigger: the position-manager call site sets `amount0Min: 0, amount1Min: 0` (a *different* field pair from the swap struct's `amountOutMinimum`), or the `'Price slippage check'` require is absent. · Test: grep every `DecreaseLiquidityParams`/`CollectParams` construction and check whether each min field is a caller-supplied parameter, a computed bound, or a literal zero. · Impact: the liquidity is removed at any realised ratio, so the full price impact is extractable by a sandwich at the exact moment of liquidation — the loss lands on the liquidator (who then declines to liquidate) or on the protocol's collateral. · FP guard: safe if the mins are derived from the underlying debt and the collateral valuation, or if the removal is followed by a solvency assertion — a fixed nonzero constant is *not* sufficient, since it does not track the position's composition.

- **`sqrtPriceLimitX96` left at zero while claiming slippage protection** — Trigger: the swap struct sets `sqrtPriceLimitX96: 0` and the only slippage defence is `amountOutMinimum` (which is itself zero in the source material). · Test: check whether any bound on the realised price exists at the call site — min-out, price limit, or an off-chain assertion in the caller. · Impact: with neither a min-out nor a price limit the swap has no execution bound at all and the entire slippage budget is available to a sandwich; the field exists and looks like a guard, which is why it survives review. · FP guard: safe if `amountOutMinimum` is meaningful (then the price limit is redundant) — the finding is the *conjunction* of both being unset, not either one alone.

- **Multi-hop swap path built from a hardcoded `bytes path`** — Trigger: `exactInput({path: HEX_CONSTANT, ...})` or a path array assembled in code, with no per-hop pool-existence or depth check and no admin-settable override. · Test: decode the path, resolve each hop's pool through the factory, and confirm each exists with non-trivial liquidity for every token the contract can hold. · Impact: if any hop's pool does not exist the swap reverts and the token is stranded (permanent loss if that was the only exit); if a hop exists with negligible depth the swap clears at an absurd price and the value is destroyed in one transaction. · FP guard: safe if the path is derived from a factory quote at execution time, or if every reachable token is proven to have a liquid path — on a live deployment resolve the pools rather than assuming the canonical tiers exist.

- **LP value derived from a reserve/TVL total that a small deposit can move** — Trigger: a redemption or collateral value computed as `(tvl ± depositAmount) * PRECISION / (supply * TARGET)` where `tvl` and the denominator are reaggregated on every call and `assetSupply` is small enough for one deposit to move the ratio. · Test: compute the marginal effect on the derived rate of a deposit of 1–10% of the asset supply, and compare the pre- and post-transaction redemption rates for a holder of the opposite token. · Impact: a small, reversible purchase shifts the aggregate across a threshold and re-prices the whole cohort's redemption — the attacker buys in cheaply, redeems the other token at the improved fixed rate, and the difference comes out of the other holders' positions. · FP guard: safe if the rate is computed from a TWAP or a supply-independent quantity, or if the supply is large enough that the required input exceeds the extractable value — state both numbers before flagging.

- **Fee-growth accounting mis-attributed when collecting owed tokens** — Trigger: `position.tokensOwed0 += amount0 + FullMath.mulDiv(feeGrowthInside0LastX128 - position.feeGrowthInside0LastX128, positionLiquidity, Q128)` — the delta is multiplied by `positionLiquidity` captured before the decrease, and the stored `feeGrowthInside*LastX128` is only valid if it was initialised at mint. · Test: for a position that has never had its fee growth initialised (never touched since mint, or touched only by the pool), read the stored value and check whether the subtraction can underflow; then check which liquidity value is used for the multiplication on a second call. · Impact: the subtraction underflows and reverts (removal impossible → bad debt), or the fees are credited against the wrong liquidity so `tokensOwed` is mis-stated — the protocol's collateral valuation then includes phantom value and over-lends against it. · FP guard: safe if the stored fee-growth baseline is refreshed on every position mutation and the same liquidity value used in the numerator is the one that earned the fees — trace the `positionLiquidity` variable rather than assuming.

- **Router "best price across pools" selection defeats a pool-type assertion** — Trigger: `(amountOut, isStable) = router.getAmountOut(PROBE, tokenIn, tokenOut); require(isStable == expected, "...wrong pool")` — the router is free to quote from whichever of two pool types offers the better price. · Test: manipulate the *other* pool so it quotes better than the expected one, then call the price-dependent path (liquidation, borrow, valuation) and check which branch reverts. · Impact: the assertion fails whenever a manipulator makes the wrong pool look better, so the entire price-dependent action is deniable — an under-collateralised borrower deliberately distorts the alternate pool to block their own liquidation and keeps the position open indefinitely. · FP guard: safe if the code queries the specific pair directly (`pairFor(token, quote, stable)` then `getAmountOut` on that pair) rather than letting the router choose; also check that the manipulator actually profits — if blocking the action only delays it, this is lower severity.

- **Fixed-size probe swap used as a price source** — Trigger: `router.getAmountOut(HUNDRED_TOKENS, ...)` where the probe amount is a hardcoded constant and the result is treated as a price. · Test: compute the probe's price impact in the pool being queried — compare the quoted output against the marginal (infinite-division) price at the pool's current reserves. · Impact: the implied price is dragged toward the probe's realised impact, so an attacker who moves the pool gets a disproportionately distorted reading from a small trade; the distortion is systematic (always in the direction of the probe) rather than noisy, so it is stackable with a real position. · FP guard: safe if the probe is small relative to pool depth (quantify the ratio) or if the result is cross-checked against an independent oracle with a bounded tolerance band.

- **Allowance increased against a pool token that already reports an infinite allowance** — Trigger: `bpt.safeIncreaseAllowance(address(vault), amount)` where Balancer-style pool tokens return `type(uint256).max` from `allowance` for the canonical spender. · Test: read the pool token's `allowance()` semantics for that spender, evaluate `oldAllowance + amount`, and check for an unconditional overflow. · Impact: the pool-exit path reverts for every user — a hard, permanent denial of service on withdrawals, and the irony is that the failing line was added as defensive practice for exactly the wrong token class. · FP guard: safe if the code uses `forceApprove`/direct `approve`, or if the token is verified not to return an infinite allowance; the pattern itself is good practice, so check the token before flagging.

- **Maximum-amount pull before a pool join with no refund of the unused balance** — Trigger: `safeTransferFrom(user, address(this), maxAmountsIn[i])` for each asset before `joinPool`, with the pool deciding the actual consumption internally and no post-call balance sweep. · Test: supply a maximum above what the pool absorbs, complete the join, and compare the contract's residual balance per asset against the user's expectation. · Impact: the unused tokens are stranded in the router — the user authorised only a *maximum* and loses the remainder; on a shared router contract the residue may also be reachable by a later caller depending on the withdrawal logic. · FP guard: safe if the router sweeps each residual back to `msg.sender` after the join, or if the pool consumes exactly the submitted amounts by construction — read the sweep, do not infer it from the allowance pattern.

- **Pool-launch gate keyed on a per-unit price rather than accumulated totals** — Trigger: `enableUniswapV3Launch` guarded by `unitPrice >= config.thresholdPrice` where the operational requirement is that enough ETH has been raised to seed the pool. · Test: solve for the number of tokens sold at which the rate condition first holds, separately solve for the number required to raise the seeding ETH, and quantify the gap (in the source material: ~8,200,000 sold to trip the gate vs ~8,355,000 needed). · Impact: the pool is seeded underfunded by the gap, so the initial liquidity is shallower than the participants were promised — the shortfall is socialised to everyone who bought on the assumption the gate was a solvency check, and it is exploitable by whoever knows the exact threshold. · FP guard: safe if the unit price is a provable sufficient statistic for the raised total (only when the token count is fixed), or if a second check covers the aggregate — look for the second gate before flagging.

- **Pool-seeding mint computed as a constant instead of `target − totalSupply()`, with no reconciliation** — Trigger: the seeding path mints a fixed or config-derived amount rather than `targetSupply - token.totalSupply()`, and no post-seed `require(totalSupply == target)` closes the gap. · Test: run two different pre-seed purchase histories that should both end at the target supply and check whether both do; also test the boundary cases just below and exactly at the launch threshold. · Impact: the final supply is off by an amount that depends on the path taken (the source material shows ~9,997,888 against a promised 10,000,000), so any downstream ratio — pool price, redemption rate, fee basis — is computed against a supply that is not what the protocol advertises. · FP guard: safe if the constant is provably the correct remainder for every reachable path (rare) or if the reconciliation assert exists; a mint that happens to be right in the tested scenario is not evidence.

## Sequence

1. **Establish the units end-to-end before touching any price code.** Pick one pair, compute its true price by hand from `slot0`, and follow that single number from the pool read → conversion → adapter return → consumer, checking the decimal factor at each hop. Mis-scaled feeds are the highest-value V3-adjacent bug class and every other price check depends on getting this right.
2. **Run the generic swap-parameter checks first** — `heuristics-core-solidity.md` entries 5–9 cover min-out, deadline, hardcoded fee tier/path, and missing fallback exits. There is no point auditing V3 mechanics if the call sites have no slippage bound at all.
3. **Enumerate every pool the protocol can touch, and resolve each one on-chain.** For each: does it exist, at which fee tier, with what depth, and what are the two tokens' decimals? Anything the protocol resolves by assumption rather than by lookup is a candidate.
4. **Audit the price path as three separate functions** — the pool read (`observe`/`slot0`), the normalisation (decimals, orientation, PriceX96), and the consumer (valuation, health, liquidation). Most findings live in the seams; check that the window is populated, the orientation is recorded, and the units match what the consumer assumes.
5. **Walk every position used as collateral.** For each: who owns the NFT, can it be mutated outside the protocol, what does the pool say its liquidity is right now, and what does the removal path require? Deposit-side validation and liquidation-side preconditions must agree.
6. **List every min-out / price-limit / tolerance field across the whole codebase** (`amountOutMinimum`, `amount0Min`, `amount1Min`, `sqrtPriceLimitX96`, tolerance bands, probe sizes) and classify each as caller-supplied, oracle-derived, or a literal that protects nothing. Then check whether the same call sets two of them to values that only work together.
7. **Trace the pool-integration entry and exit paths for value that stays behind** — residual balances after a join, allowance arithmetic against pool tokens, and paths where the router chooses the pool rather than the protocol.
8. **Do the launch/seeding arithmetic on paper.** For each activation gate, solve for the condition boundary and compare it against the operational requirement; for each supply-reconciliation step, run two different histories to the same target.
9. **For each finding that survives, write the falsifier before writing it up** — a price computed by hand, an assertion, or a one-line test. If none can be written, it is a heuristic candidate, not a finding.
