## Workflow (what was validated)

1. PULL — mechanical, do it yourself, never delegate.
   - GET https://api.llama.fi/protocols (full list ~8k, ~9MB). **CORRECTED 2026-09-22 — the list endpoint DOES carry these fields; what is unreliable is COVERAGE, not existence.** Measured over 8,324 protocols: `github` present on **1,584 (19%)**, `audit_links` on **2,871 (34%)**, `address` on **4,264 (51%)**, `listedAt` on **6,648 (80%)**, `forkedFromIds` on **2,089 (25%)**, `tvl` on **7,109 (85%)**. `audits` is **NOT a count — CORRECTED 2026-09-24 by direct measurement: it is a STRING with a two-value set, observed only `'0'` and `'2'`** (present on 8,339/8,352 rows); treat it as a boolean-ish "has some audits recorded" flag. **Never convert it with `int()`** — an `isinstance(x, int) else 0` conversion silently turns `'2'` into 0 and reports an audited protocol as unaudited, with no error anywhere (this exact bug appeared in the campaign's own enrichment pass on 2026-09-24 and corrupted a whole ranking column). And `audits == '0'` at HIGH TVL is usually a **DATA GAP, not a signal**: verified false zeros include `ether.fi Stake` ($5,188M), `mETH Protocol` ($631M), `Coinbase Wrapped Staked ETH` ($512M), `Hyperlane` and `Polymarket`. It is therefore weakest evidence exactly where TVL is highest — confirm audit reality from the protocol's OWN docs/audit page, and expect high-TVL zero-audit lists to die on **crowding (G11d)**, not on being unaudited. Full measurement: references/sourcing-funnel-calibration.md. The old wording — "the LIST endpoint has NO github / audit_links fields" — was wrong and cost budget: it sent every pass to a per-protocol fetch for a field that is already there 19% of the time (34% for `audit_links`). `tvl` is NULLABLE — coalesce to 0.
   - Filter: listedAt within 90d window (R1 widened from 45-60d), tvl >= ~150k, drop categories with no contract surface (see playbook). Shortlist gates per methodology R1: (a) full-fleet source verification — GitHub OR explorer-verified for 100% of fund-facing contracts, checked at shortlist time; (b) own-code depth — thin hook/wrapper/minimal-logic cores excluded even when unaudited. A "clean, small core" target yields config notes, not exploits. Enrich top ~25-45 slugs via the detail endpoint (sequential urllib is fine).
   - REPEAT DISCOVERY PASSES (2nd pass over an overlapping window, validated 2026-09-07): before re-pulling, read the previous campaign's TARGET_SELECTION_REPORT.txt + data/ (Desktop/audit<N>/…). Hard disqualifications PERSIST across passes — phantom/DNS-dead, zero-source, off-chain-custody backing, TVL artifact, post-exploit limbo, permissioned + freshly-audited — skip them without re-research. Re-check only (a) names newly inside a widened recency window, (b) targets a RULE CHANGE re-opened (e.g. closed-GitHub-but-explorer-verified became eligible under R1 → HertzFlow-type re-checks). Skipping the old report re-burns a full recon fan-out on already-ranked names.

2. CLASSIFY before fan-out — do not burn subagent time on junk.
   - Spam clusters: identical short descriptions across many listings (e.g. five "Prop AMM on Solana" entries with referral-link URLs) → drop wholesale.
   - Phantom listings: big TVL + dead website. Probe socket.gethostbyname on www/apex/docs/app hosts; dead everywhere + no news = zombie (found: AZverse, claimed $51.8M, domains DNS-dead, only a bare GitHub org).
   - Audit count on DeFiLlama is UNRELIABLE both directions — never score from it. Real case: Arcus Perps showed audits=0 while Trail of Bits (2026-06 review PDF on github) + OpenZeppelin audits exist.
   - TVL realism: huge +% 7d right after listing = often adapter artifact or points-farming/team liquidity. Perp venues often run off-chain matching (REST/WS "exchange" APIs) — contracts matter less when risk sits in an off-chain engine or custody.

3. RECON: inline and in sequence by default (2026-10-01: no subagents unless he says so). If he says fan out: parallel recon subagents, disjoint sets, orchestrator preps shared facts.
   - Seed every child with parent-fetched metadata (slug, TVL, listed date, chains, url, DL audit strings, any GitHub hint) so they don't re-fetch it.
   - Brief is RECON ONLY — no vulnerability hunting until a target is chosen.
   - Output contract: one structured JSON object per protocol with UNKNOWN convention (never guess), evidence URLs for nonzero facts, and an explicit audit_candidate_verdict + reason.
   - Budget shared resources: unauthenticated GitHub API = 60 req/hr PER IP and parallel children share that IP → cap ~12 api.github.com calls/child and mandate the HTML fallback.

4. AGGREGATE + CROSS-CHECK — child self-reports are not verified facts. Independently spot-check the top contenders yourself (audit existence/date/scope, code public, TVL realism). Specifically watch: audits predating the deployed version; "audited" covering only a wrapper; off-chain-dominant protocols where contracts are not the real risk surface.

5. SCORE then decide qualitatively. Implement the rubric in code (deterministic, no arithmetic slips in the head), but the shortlist is qualitative — the user's rule: a score of 80 is NOT automatically better than 70. Deliver Top-10 table + Top-3 analysis + ONE primary target, then STOP (no deep audit work until the user greenlights Phase 6+).
   - DELIVERABLE SHAPE (user preference, stated 2026-09-10): TWO files. (a) a ranked report — Top-10 in qualitative order with a RE-RANK NOTE whenever that order departs from the raw scores, Top-3, ONE primary, and a kill ledger naming the gate that killed each rejection; (b) ONE consolidated readable catalogue of EVERY verified protocol — index grouped by verdict (index order != ranking order, so give the index a rank column), full detail on the survivors (contracts with OK/UNV flags, every audit with firm/date/scope/url, the deploy-vs-audit gap, custody, own code, numbered hypotheses, evidence URLs), then the rejections and their reasons, then caveats. He asked for this explicitly: "so that I can read them all cleaner". Generate it with scripts/build_findings_catalogue.py from the agent JSONs, and mark each claim [ORCHESTRATOR-VERIFIED] vs agent-reported. He then verifies the protocols himself and names the target — never assume the pick, never auto-start Phase 6.

## Pitfalls (learned the hard way)

- **THE PLATFORM CHANNEL REOPENED 2026-09-22 — AND IT REOPENS *BEHIND* A GATE PASS, NOT IN FRONT OF ONE.** The user withdrew Immunefi/HackenProof on duplicate risk (2026-09-16, recorded above) and reopened it on 2026-09-22: *"we will be hunting for bugs on platforms like immunefi and other platforms."* **This is a user decision, not a re-proposal** — `paying-program-channels.md` stays superseded *as a strategy*, and nothing here undoes the withdrawal record. What must change with the reopening is that it carries the layer whose absence caused the withdrawal: **G11, the platform gate pass, which runs ABOVE G10 and G8 and BEFORE any code is read** (defined in `defi-audit-engine/SKILL.md`): G11a PLATFORM (KYC; pay-to-submit fee weighed against *probability*, not the bounty headline; **an attack-window restriction means a submission outside it is INVALID, not late**) → G11b SCOPE (address/pinned commit in scope, right chain, as a `smart_contract` asset — and **read the out-of-scope list before the code**: programs routinely exclude the class you are best at, "admin risk" / "oracle manipulation" / "known issues" / "centralisation") → G11c DUPLICATE → G11d CROWDING (prior-audit count **verified, never quoted** — it is the buyer's own field). **G11c's honest limit: on Immunefi there is NO public list of submitted findings, so novelty can never be PROVEN** — dedup is probabilistic by construction, and anyone who claims otherwise is guessing. The mitigation is not a checklist, it is a **targeting rule**: prefer surfaces where a duplicate is *structurally unlikely* — degenerate-input guards, asymmetric state transitions (a flag set with no reset path), variable mixups in multi-recipient fee paths, **fork diffs** (the base is maximally crowded, the *diff* is unread), vertical mechanisms — and deprioritise what Slither finds (generic reentrancy, spot-price oracle, generic access control, ERC-4626 rounding, standard proxy issues). **Do NOT split one root cause into adjacent submissions on a platform channel** — rational on Code4rena (auto-dedup, no validity penalty), actively harmful on Immunefi (duplicates rejected outright; repeat offenders lose standing). If the local dedup source is a stub (`SWEEP/solodit_custom.md` measured **10 lines** on 2026-09-22), that is a **coverage gap that BLOCKS the pass**, never a green light. v8 doctrine: `Desktop/audit2/STRATEGY_v8.md`.
- **A "found a medium on platform X yesterday" claim needs measuring BEFORE it calibrates strategy (2026-09-22).** The peer repo `Misbah-Engr/Audit-Reports-and-POCs` was described as a medium found on Immunefi *yesterday*. Measured: **no Immunefi report at all** — the population is Code4rena (Thorwallet, Legion), **HackenProof** (Reliq High+Low), Remedy/`hunt.r.xyz` (Celo, UFarm) and one private PDF; newest report **12 Jan 2026**; last commit **2026-05-03**; and the "medium" is a **Code4rena** submission closed as a duplicate-adjacent pair (`F-7/S-243` + `S-98`).
